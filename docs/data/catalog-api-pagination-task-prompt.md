# 공고 목록 서버 검색·페이징 전환 작업 지시

현재 사용자 화면은 `/api/overview`로 전체 공고와 상세정보를 받아 브라우저에서 검색·필터링한다. 공고 수가 늘어도 첫 화면과 검색이 안정적으로 동작하도록, 공고 목록 조회를 서버 검색·정렬·페이징 API로 전환한다.

## 목표

- 사용자 목록 화면은 현재 표시할 페이지의 공고만 요청한다.
- 지역, 임대 유형, 모집 상태, 공고명 검색어, 보증금 상한, 월세 상한, 전용면적 최소·최대 조건을 서버에서 적용한다.
- 공고 카드에 필요한 지역·보증금·월세·전용면적·접수 마감일은 DB 상세정보를 우선 사용하되, 값이 없으면 기존 목록값 또는 `공고문 확인` 규칙을 유지한다.
- 검색 조건을 입력하는 동안에는 기존 목록을 유지하고, `검색` 버튼을 눌렀을 때만 새 조건을 적용한다.
- 기존 URL hash 메뉴 전환, 상세 Drawer, 관심 조건, 수동 수집 후 갱신 동작을 유지한다.

## API 계약

`GET /api/announcements`

쿼리:

- `page`: 1부터 시작, 기본 1
- `size`: 기본 10, 최대 50
- `region`
- `housingType`
- `status`
- `query`: 공고명 검색어
- `depositMaxWon`
- `rentMaxWon`
- `areaMin`, `areaMax`
- `sort`: `LATEST`, `DEADLINE`, 기본 `LATEST`
- `includeClosed`: 기본 `false`
- `includeUnknown`: 기본 `true`. `false`면 위치·보증금/월세·면적이 모두 확인된 공고만 반환
- `savedId`: 저장 공고 ID를 반복 전달. 전달하면 해당 ID만 검색
- `interestOnly`, `interestRegion`(반복), `interestDepositMaxWon`, `interestRentMaxWon`, `interestAreaMin`, `interestAreaMax`, `interestIncludeUnknown`: 관심 조건을 서버에서 함께 적용

응답:

```json
{
  "items": [],
  "page": 1,
  "size": 10,
  "totalCount": 0,
  "hasNext": false,
  "appliedFilters": {}
}
```

## 백엔드 설계

- `AnnouncementRepository`에 목록 전용 조회를 추가한다.
- 목록 정렬·필터·페이징은 SQL에서 처리한다. 상세정보가 없는 공고도 누락시키지 않도록 `LEFT JOIN` 또는 상관 서브쿼리를 사용한다.
- 보증금·월세 조건은 같은 `rental_options` 행 안에서 동시에 만족해야 한다.
- 다중 단지·다중 주택형 공고는 한 공고를 한 번만 반환한다.
- 페이지 범위와 숫자 파라미터를 검증하고 잘못된 값은 `400`으로 응답한다.
- `/api/overview`는 홈 화면에 필요한 작은 요약 데이터만 유지한다. 전체 공고 배열·전체 상세 맵을 더 이상 사용자 첫 화면에 포함하지 않는다.
- 수동 수집 완료 후 프론트는 현재 적용 검색 조건의 첫 페이지를 다시 조회한다.

## 프론트 설계

- `draftFilters`와 `appliedFilters`를 분리한다.
- 검색 버튼: `page=1`로 서버 요청 후 결과 교체.
- 초기화 버튼: 입력과 적용 조건을 초기값으로 되돌린 뒤 첫 페이지 요청.
- `공고 n건 더 보기`는 서버의 다음 페이지를 요청해 기존 목록 뒤에 추가한다. `hasNext=false`면 숨긴다.
- 로딩 중 검색 버튼과 더 보기 버튼을 비활성화하고, 기존 결과는 유지한다.
- 요청 취소를 위해 `AbortController`를 사용하고, 늦게 도착한 이전 요청이 최신 결과를 덮어쓰지 않게 한다.
- 검색 결과 건수, 빈 결과, 오류, 더 보기 완료 상태를 `aria-live`로 안내한다.
- Drawer는 목록 카드의 요약 데이터로 열되, 상세 API가 필요한 기존 경로가 있으면 유지한다.

## 테스트·완료 기준

1. 지역·유형·상태·제목·금액·면적 조건이 서버에서 정확히 필터링된다.
2. 보증금과 월세가 서로 다른 임대조건 행을 조합해 일치로 판단하지 않는다.
3. 마감 공고 제외 기본값, 포함 옵션, 최신순·마감임박순 정렬을 검증한다.
4. 전체 건수, 페이지, 다음 페이지 여부가 정확하다.
5. 프론트는 `/api/overview`의 전체 공고 데이터에 의존하지 않고 목록 API를 요청한다.
6. 검색 버튼 전까지 입력 조건이 결과에 적용되지 않는다.
7. 다음 페이지 추가, 빈 결과, 오류, 수동 수집 후 첫 페이지 재조회가 동작한다.
8. 기존 Spring·Node 테스트를 모두 통과한다.

## 제약

- 외부 라이브러리와 별도 캐시 서버를 추가하지 않는다.
- 기존 DB 구조와 상세 Drawer API를 최대한 재사용한다.
- 사용자 공고 검색에 관리자용 수집·PDF 검토 정보를 노출하지 않는다.
