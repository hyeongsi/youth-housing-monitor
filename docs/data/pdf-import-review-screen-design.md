# 사이트별 PDF 자동 추출·검토 입력 화면 설계

> 구현 상태: 기존 정적 화면 기준 설계. PDF 입력·근거·검증·확정 규칙은 유지하되, React 전환 이후 화면 파일·컴포넌트·경로 기준은 [React 프론트엔드 전환 아키텍처](../ui/react-frontend-architecture.md)를 우선한다.

## 1. 목표

관리자가 청약 사이트와 기존 공고를 선택하고 PDF를 업로드하면 사이트 전용 파서가 필요한 정보를 후보값으로 추출한다. 관리자는 PDF 원문 근거와 추출값을 함께 확인·수정하고, 검증을 통과한 값만 SQLite의 공고 상세 구조에 저장한다.

자동 추출은 저장 완료가 아니라 **입력 초안 생성**이다. 정확한 값은 사용자가 검토하고 `확정 저장`을 눌렀을 때만 운영 데이터가 된다.

## 구현 상태 (2026-11-10)

서울 청년안심주택 민간임대 PDF에 대해 구현을 완료했다.

- `SeoulYouthSafePrivatePdfParser`는 특정 공고의 고정값이 아니라 주택개요·공급일정 및 청약·공급현황·신청자격 및 제출서류 섹션, 표 헤더, 좌표를 기준으로 후보를 추출한다.
- 사이트·단지·주택형·호실·임대조건·기관 역할·일정·신청조건은 모두 반복 행으로 수정·추가·삭제할 수 있다.
- 각 근거는 페이지·원문·좌표·추출 방식·검토 상태를 보관한다. 사용자가 바꾼 값은 `MANUAL`과 `MANUALLY_REVIEWED`로 남긴다.
- 화면에는 영문 코드 대신 한글 라벨을 표시한다. 내부 API·DB 코드값은 유지한다.
- OCR은 아직 추가하지 않았다. 텍스트 레이어가 없는 PDF는 자동 확정하지 않고 검토 필요 상태로 남긴다.

## 2. 용어와 데이터 기준 보완

### 공고 기본정보

공고명, 공급기관, 공고일, 접수 기간, 모집 상태, 공식 URL은 기존 목록 HTML 수집 결과를 우선 사용한다. PDF 업로드 화면에서는 새로 입력하기보다 DB의 기존 공고를 검색해 연결한다.

PDF 값과 HTML 값이 다르면 자동으로 덮어쓰지 않고 `값 불일치` 경고를 표시한다.

### 주택개요

다음 값을 각각 분리한다.

- 단지명
- 도로명·지번 주소
- 총 세대수
- 해당 공고 공급호수
- 시행사
- 임대사업자
- 시공사
- 입주 예정 기간

시행사, 임대사업자, 시공사는 같은 회사일 수 있지만 역할별로 저장한다.

### 공급호수와 층·호

`공급호수`와 `층·호`는 다른 값이다.

- 공급호수: 이번에 공급하는 주택의 개수. 예: `1세대`
- 동·층·호: 개별 공급 주택의 실제 위치. 예: `24층`, `2405호`

PDF에 개별 호실이 모두 나열되어 있으면 호실 수로 공급호수 후보를 계산할 수 있지만, 원문에 명시된 공급호수와 다르면 자동 확정하지 않는다.

### 주택형

다음 값을 한 행으로 묶는다.

- 공급 유형: 신혼부부 특별공급 등
- 주택형: `36B`
- 전용면적: `36.65㎡`
- 공급호수: `1`
- 동·층·호 목록: `24층 2405호`

전용면적과 공급면적은 서로 다른 필드로 관리한다. PDF에 `전용면적`만 있으면 공급면적을 추정하지 않는다.

### 임대조건

보증금과 월세는 반드시 같은 주택형·같은 조건 행으로 저장한다.

- 보증금
- 월 임대료
- 관리비
- 보증금 전환 조건
- 근저당권 금액
- 임대보증금 보증금액
- 보증보험 만료일

금액은 다음 세 값을 함께 보존한다.

- 원문값: `151,000,000`
- 원문 단위: `만원` 또는 `원`
- 정규화 금액: `151000000원`

원문 단위와 금액 자릿수가 충돌하면 자동 환산하지 않고 `단위 확인 필요`로 표시한다.

### 신청조건

`순위` 하나로 저장하지 않고 조건 종류별로 분리한다.

- 공급 유형·특별공급 대상
- 연령
- 무주택 조건
- 세대 구성 조건
- 소득 순위와 가구원 수별 기준금액
- 자산 기준
- 자동차가액 기준
- 지역 순위
- 대학·직장 소재지 조건
- 기타 신청 제한

소득 기준은 `순위 × 가구원 수` 형태의 행렬이므로 각 셀을 독립된 기준 행으로 저장한다.

### 일정

일정은 이벤트 종류, 시작·종료 시각, 상태로 분리한다.

- 공고일
- 청약 접수
- 서류 제출
- 당첨자 발표
- 계약 체결
- 입주 지정 기간

PDF에 연도가 생략된 월·일만 있으면 공고일 연도를 후보로 사용하되, 12월 이후 1월처럼 연도가 넘어가는 경우 다음 해로 계산하고 `연도 추론` 표시를 남긴다.

## 4. 사이트별 파서 관리

### 사이트 선택

첫 화면에서 관리자가 사이트를 직접 선택한다.

- 서울특별시 청년안심주택
- SH
- LH
- 서울주거포털

사이트 선택값으로 파서를 결정한다. PDF 내용만 보고 사이트를 임의 추정하지 않는다.

### 파서 식별자

```text
SEOUL_YOUTH_SAFE_PRIVATE_V1
SH_RENTAL_NOTICE_V1
LH_RENTAL_ATTACHMENT_V1
```

파서는 `사이트 + 문서 유형 + 버전`으로 구분한다. 같은 사이트라도 민간임대, 공공임대, 당첨자 발표처럼 문서 구조가 다르면 별도 파서를 사용한다.

### 서울 청년안심주택 민간임대 V1 규칙

섹션 제목을 우선 탐색한다.

- `[주택개요]`
- `[공급일정 및 청약]`
- `[공급현황]`
- `[신청자격 및 제출서류]`
- `[당첨자발표]`
- `[별첨]`

필드명은 사이트별 별칭 사전을 사용한다.

| 표준 필드 | 인식할 별칭 |
| --- | --- |
| 단지명 | 단지명, 주택명, 사업명 |
| 시행사 | 시행사, 사업주체 |
| 임대사업자 | 임대사업자, 임대인 |
| 시공사 | 시공사, 건설사 |
| 전용면적 | 주거전용, 전용면적, 전용 |
| 보증금 | 보증금액, 임대보증금, 보증금 |
| 월세 | 임대료, 월임대료, 월세 |
| 접수 | 청약신청, 접수기간, 신청기간 |

표는 제목만 찾지 않고 필요한 헤더 조합으로 확인한다. 예를 들어 공급현황 표는 `공급유형 + 전용면적 + 공급호수 + 보증금 + 임대료` 중 네 개 이상이 있어야 한다.

### 추출 단계

1. PDF 텍스트 레이어와 페이지별 글자 좌표 추출
2. 섹션 제목과 표 영역 탐색
3. 사이트별 별칭으로 필드 후보 생성
4. 금액·면적·날짜·층·호 정규화
5. 교차 검증과 중복 검사
6. 근거 좌표와 함께 초안 저장
7. 사용자 검토 후 운영 DB 반영

텍스트 레이어가 없을 때만 OCR을 사용한다. OCR 결과는 항상 `검토 필요` 상태로 시작한다.

## 5. 입력 화면 구조

관리자 전용 `/admin-import.html` 화면으로 분리한다.

### 단계 1. 공고와 PDF 선택

```text
[PDF 상세정보 가져오기]

┌ 사이트·문서 유형 ┐ ┌ 기존 공고 검색·선택 ┐ ┌ 공고문 PDF ┐ [PDF 분석 시작]
서울 청년안심주택    검색 결과·선택 안내       파일명 표시
```

기존 공고 연결은 필수다. 목록 HTML에서 이미 수집한 공고 기본정보를 재사용하고 PDF 상세만 추가한다.

업로드 전 확인:

- PDF만 허용
- 최대 파일 크기 제한
- 파일 hash로 중복 업로드 확인
- 암호화 PDF 거부
- 페이지 수와 텍스트 레이어 유무 확인

### 단계 2. 자동 분석

```text
PDF 확인          완료
페이지 분석       4 / 4
주택개요          발견
공급현황 표       발견
신청조건          발견
일정              발견
```

가짜 퍼센트를 만들지 않고 실제 완료한 단계만 표시한다. 실패한 단계가 있어도 나머지 추출 결과는 검토할 수 있게 한다.

### 단계 3. 추출 결과 검토

현재 데스크톱 구현은 세 영역 작업 공간이다. 긴 입력폼 때문에 PDF와 근거를 계속 찾아 내려가는 문제를 막기 위해 PDF 원문·근거는 sticky로 고정한다.

```text
┌ PDF 원문 ┐ ┌ 추출 데이터 편집 ┐ ┌ 선택한 원문 근거 ┐
│ 페이지 이동 │ 단지·주택 탭      │ 페이지·추출 방식   │
│             │ 일정 탭            │ 검토 상태·원문값   │
│             │ 신청조건 탭        │ 근거 목록           │
└─────────────┴───────────────────┴───────────────────────┘
```

- 상단 요약은 단지·주택, 임대조건, 일정, 신청조건의 추출 여부를 먼저 보여 준다.
- 입력 필드의 `근거 n쪽`을 누르면 PDF가 해당 페이지로 이동하고, 오른쪽 근거 패널에 원문·추출 방식·검토 상태가 표시된다.
- 좁은 화면에서는 한 열로 전환하고 sticky를 해제한다.

근거 상태의 화면 표시와 내부 값은 다음과 같다.

| 화면 표시 | 내부 값 | 의미 |
| --- | --- | --- |
| 원문 일치 | `MATCHED` | 명확한 표 셀이나 라벨에서 추출 |
| 검토 필요 | `NEEDS_REVIEW` | 단위·연도·표 연결을 확인해야 함 |
| 확인 완료 | `CONFIRMED` | 관리자가 원문을 확인함 |
| 수동 확인 완료 | `MANUALLY_REVIEWED` | 사용자가 직접 수정·확인함 |

### 주택개요 폼

```text
단지명          [세이지움 개봉________________]
주소            [서울특별시 구로구 개봉동 503번지 일원]
위치 안내       [1호선 개봉역 1번 출구_______]
총 세대수       [605] 세대
이번 공급호수   [1] 세대

기관 역할
[시행사 ▼]      [개봉아이알디피에프브이(주)] [+ 추가]
[시공사 ▼]      [태영건설__________________] [삭제]
```

### 공급현황·임대조건 폼

공급 주택은 반복 가능한 행으로 구성한다.

```text
공급유형       주택형   전용면적   공급호수   동·층·호
신혼 특별공급  36B      36.65㎡    1          24층 2405호

보증금 원문       [151,000,000]   원문 단위 [만원 ▼]
정규화 보증금     [151,000,000]원  ⚠ 단위 확인 필요
월세 원문         [354,600]       원문 단위 [만원 ▼]
정규화 월세       [354,600]원      ⚠ 단위 확인 필요
```

주택형 행을 선택한 상태에서 임대조건을 편집하게 하여 다른 주택형의 보증금과 월세가 섞이지 않도록 한다.

### 신청조건 폼

기본 조건과 순위 표를 나눈다.

```text
기본 조건
[연령]       만 [19]세 이상 ~ [39]세 이하
[주택소유]   신청자 및 입주 예정 세대원 전부 무주택
[자동차]     [45,420,000]원 이하
[자산]       대상 [청년] [251,000,000]원 이하

순위 조건
종류 [지역 ▼] 순위 [1] 지역 [서울특별시 구로구]
종류 [소득 ▼] 순위 [1] 가구원 [1] 기준 [3,813,363]원 이하
```

한 문장으로 표현하기 어려운 조건은 원문 설명을 함께 저장한다.

### 일정 폼

```text
이벤트             시작                    종료                    상태
청약 신청          2026-11-09 09:00       2026-11-10 23:00       확정
당첨자 발표        2026-11-12             2026-11-13             이메일 안내
계약 체결          2026-11-18 10:00       2026-11-20 17:00       확정
입주 지정 기간     2026-12-11 10:00       2027-01-08 15:00       확정
```

날짜만 있는 경우 시간을 비워 둔다. `예정` 문구가 있으면 상태를 예정으로 저장한다.

### 단계 4. 검증과 저장

오른쪽 하단에 검증 결과를 고정 표시한다.

```text
저장 전 확인
✓ 기존 공고와 연결됨
✓ 주소 확인
✓ 공급호수와 호실 수 일치
! 보증금 원문 단위 확인 필요
! 월세 원문 단위 확인 필요

[초안 저장] [확정 저장]
```

경고가 있어도 초안은 저장할 수 있다. 금액 단위 충돌, 공고 연결 누락, 주택형 없는 임대조건처럼 데이터 의미를 깨뜨리는 오류가 있으면 확정 저장을 막는다.

## 6. 자동 검증 규칙

### 필수 오류

- 기존 공고가 연결되지 않음
- 단지 또는 주소가 모두 없음
- 임대조건이 주택형과 연결되지 않음
- 보증금·월세 정규화 단위를 결정하지 못함
- 동일 공고·동일 문서 hash가 이미 확정됨
- 시작일이 종료일보다 늦음

### 경고

- 원문 공급호수와 개별 호실 수 불일치
- 제목·공급기관이 HTML 목록과 PDF에서 다름
- 원문 단위와 금액 자릿수가 충돌
- 전용면적이 일반적인 범위를 벗어남
- 월·일만 있어 연도를 추론함
- OCR로 추출함
- 시행사와 임대사업자의 역할이 불명확함

## 7. DB 저장 설계

기존 테이블을 우선 재사용한다.

- `announcements`: 연결된 공고
- `housing_sites`, `locations`, `announcement_sites`: 단지·주소·입주 정보
- `supply_units`: 공급 유형, 주택형, 전용면적, 공급호수
- `rental_options`: 보증금, 월세, 관리비, 전환조건
- `announcement_documents`: PDF URL·hash·저장 경로·파서 버전·상태

추가가 필요한 최소 테이블:

### `document_extractions`

PDF 분석 초안과 검토 상태를 저장한다.

- `id`
- `announcement_document_id`
- `parser_id`, `parser_version`
- `status`: `ANALYZING`, `DRAFT`, `READY`, `COMMITTED`, `FAILED`
- `extracted_json`
- `validation_json`
- `created_at`, `reviewed_at`, `committed_at`

### `extraction_evidence`

각 입력값의 원문 근거다.

- `extraction_id`
- `field_path`: `sites[0].units[0].exclusiveAreaM2` 등
- `page_number`
- `bounding_box_json`
- `raw_text`
- `method`: `TEXT`, `TABLE`, `OCR`, `MANUAL`
- `review_status`: `MATCHED`, `NEEDS_REVIEW`, `CONFIRMED`

### `supply_rooms`

개별 동·층·호를 저장한다.

- `supply_unit_id`
- `building_text`
- `floor_text`
- `room_text`
- `source_text`

### `site_organizations`

기관의 역할을 구분한다.

- `announcement_site_id`
- `role`: `DEVELOPER`, `LANDLORD`, `CONTRACTOR`, `OPERATOR`
- `organization_name`

### `announcement_events`

- `announcement_id`
- `event_type`
- `starts_at`, `ends_at`
- `status`: `CONFIRMED`, `EXPECTED`, `INFERRED`
- `description`

### `eligibility_rules`

- `announcement_id`
- `category`: `AGE`, `HOUSING`, `INCOME`, `ASSET`, `VEHICLE`, `REGION`, `HOUSEHOLD`, `OTHER`
- `target_group`
- `rank`
- `household_size`
- `operator`
- `threshold_value`, `threshold_unit`
- `description`

### `announcement_detail_revisions`

확정 저장 또는 복원으로 바뀌기 직전·직후의 사용자용 상세 스냅샷을 보관한다.

- `announcement_id`: 대상 공고
- `action`: `PDF_COMMITTED`, `RESTORED`
- `extraction_id`, `document_hash`: 확정에 사용한 PDF 분석 초안과 원본 hash. 복원 이력은 비어 있을 수 있다.
- `source_revision_id`: 복원의 기준이 된 이력
- `before_json`, `after_json`: 단지·주택형·임대조건·기관·호실·일정·신청조건 전체 스냅샷
- `created_at`: 작업 시각

확정 저장은 상세 계층 교체, 운영 보조 데이터 교체, PDF 상태 변경, 이력 저장을 하나의 트랜잭션으로 실행한다. 중간에 실패하면 운영 상세정보와 이력 모두 남기지 않고 분석 초안만 유지한다. 복원은 선택한 이력의 `after_json`을 다시 적용하고, 그 결과를 `RESTORED` 이력으로 새로 기록한다.

## 8. API 설계

| API | 역할 |
| --- | --- |
| `GET /api/admin/announcements?query=` | 연결할 기존 공고 검색 |
| `POST /api/admin/document-imports` | 사이트·문서 유형·공고 ID·PDF 업로드 |
| `GET /api/admin/document-imports/{id}` | 분석 상태와 추출 초안 조회 |
| `PATCH /api/admin/document-imports/{id}` | 사용자가 수정한 초안 저장 |
| `POST /api/admin/document-imports/{id}/validate` | 저장 전 검증 |
| `POST /api/admin/document-imports/{id}/commit` | 운영 DB에 확정 저장 |
| `GET /api/admin/document-imports/{id}/document` | 검토용 PDF 제공 |
| `GET /api/admin/announcements/{announcementId}/detail-revisions` | 공고별 확정·복원 이력 조회 |
| `GET /api/admin/announcements/{announcementId}/detail-revisions/{revisionId}/diff` | 이전값·이후값의 항목별 비교 조회 |
| `POST /api/admin/announcements/{announcementId}/detail-revisions/{revisionId}/restore` | 선택한 확정본으로 복원 |

업로드 파일명으로 저장 경로를 만들지 않는다. 서버가 생성한 ID와 content hash를 사용하고, 파일 크기·MIME·PDF signature를 확인한다.

## 9. 구현 파일 계획

### 백엔드

- `DocumentImportController.java`: 업로드·조회·검증·확정 API
- `DocumentImportService.java`: 임시 저장, 파서 실행, 검증, commit
- `DocumentParser.java`: 여러 사이트 파서가 공통으로 지킬 결과 계약
- `SeoulYouthSafePrivatePdfParser.java`: 이번 문서 형식 전용 파서
- `DocumentExtractionRepository.java`: 초안·근거 저장
- `AnnouncementRepository.java`: 검토 완료 데이터를 기존 상세 계층에 반영
- `PdfTextLayoutExtractor.java`: PDFBox 기반 페이지 글자·좌표 추출

사이트별 파서가 실제로 두 개 이상 추가될 예정이므로 `DocumentParser` 계약과 parser ID registry는 필요하다. 범용 규칙 엔진이나 별도 스크립트 언어는 만들지 않는다.

### 프론트

- `public/admin-import.html`
- `public/admin-import.js`
- `public/admin-import.css`
- `public/admin.html`: `PDF 상세정보 가져오기` 이동 링크 추가

외부 UI 라이브러리는 추가하지 않고 기존 관리자 화면의 버튼·토스트·색상 변수를 재사용한다.

## 11. 완료 기준

- 사이트와 기존 공고를 선택하고 PDF를 업로드할 수 있다.
- 첨부 문서에서 단지명, 주소, 시행사, 시공사, 주택형, 면적, 공급호수, 층·호, 보증금, 월세, 신청조건, 일정을 후보로 추출한다.
- 모든 후보에 PDF 페이지·원문·위치 근거가 연결된다.
- 금액 단위 충돌과 연도 추론을 자동 확정하지 않는다.
- 사용자가 수정한 값을 초안으로 저장하고 다시 열 수 있다.
- 확정 저장 시 기존 정규화 상세 테이블과 추가 조건·일정 테이블에 트랜잭션으로 반영한다.
- 저장 후 기존 공고 상세 Drawer에서 단지·주택형·임대조건을 확인할 수 있다.
- 같은 PDF를 중복 확정하지 않는다.
- 스캔 PDF는 OCR 사용 여부와 검토 필요 상태가 명확히 표시된다.
