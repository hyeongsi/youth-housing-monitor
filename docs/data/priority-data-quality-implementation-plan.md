# 우선 데이터 품질 개선 구현 계획

작성일: 2026-11-12

## 범위와 순서

이번 작업은 서로 영향을 최소화하도록 다음 세 단위로 나눈다.

1. PDF 확정 전 근거 검토 강제
2. 공고 검색의 `추가모집만 보기` 서버 필터 적용
3. 기관별 PDF 파서 확대

각 단위는 구현 후 자동 테스트와 코드 검토를 통과해야 다음 단위로 진행한다. 수집·사용자 카드·상세 조회의 기존 API 계약은 유지한다.

## 1. PDF 확정 전 근거 검토 강제

### 문제

초안에 `NEEDS_REVIEW` 근거가 남아 있어도 현재 검증은 주로 단지·주택형·금액 단위·일정의 형식만 확인한다. 따라서 검토자가 모든 원문 근거를 확인하지 않은 채 확정할 수 있다.

### 결정

- `MATCHED`, `NEEDS_REVIEW`는 자동 추출 상태이며 확정 불가다.
- `CONFIRMED`, `MANUALLY_REVIEWED`만 사람이 검토한 상태로 본다.
- 삭제되지 않은 모든 근거는 위 두 상태 중 하나여야 한다.
- 사람이 추가한 값은 해당 필드의 `MANUALLY_REVIEWED` 근거가 있어야 한다.
- 검증 결과는 미확인 근거의 필드 경로와 총건수를 오류로 반환한다. 화면은 확정 버튼을 누른 뒤에도 이 오류를 그대로 보여 준다.
- 확정된 상세의 상태는 모든 근거 검토가 끝난 경우에만 `PARSED`가 된다. 자동 파서가 확정 상태를 만들지 않는다.

### 변경 대상

| 파일 | 변경 |
| --- | --- |
| `DocumentImportService.java` | `validateDraft`에서 근거 검토 상태를 검사하고 확정 직전에도 재검사 |
| `DocumentImportTests.java` | 미검토 근거가 있으면 검증·확정 실패, 전부 확인 후 확정 성공 테스트 |
| `public/admin-import.js` | 검증 오류가 이미 표시되는 흐름을 유지하고 문구가 한글로 보이는지 확인 |

### 완료 기준

- `NEEDS_REVIEW` 또는 `MATCHED` 근거가 하나라도 있으면 확정되지 않는다.
- 모든 근거를 확인 완료/수동 확인 완료로 바꾼 뒤 기존 필수값 검증까지 통과하면 확정된다.
- 실패한 확정은 운영 상세·이력에 어떤 변경도 남기지 않는다.

## 2. 추가모집만 보기 서버 필터

### 문제

사용자 화면은 `supplementalOnly=true`를 보내지만 API와 SQL 조건이 받지 않아 결과가 바뀌지 않는다.

### 결정

- 추가모집 여부는 수집 원문의 `status` 또는 `title`에 `추가모집`이 포함되는 경우로 판정한다. 원문 상태는 보존한다.
- 이 값은 진행 상태(`OPEN`, `UPCOMING`, `CLOSED`, `UNKNOWN`)와 독립된 모집 방식 조건이다. 두 조건이 동시에 적용된다.
- 별도 DB 열이나 수집 데이터 마이그레이션은 이번 범위에 추가하지 않는다. 현 검색 데이터에 바로 적용 가능한 서버 조건을 사용한다.
- API 응답의 `appliedFilters`에 `supplementalOnly`를 포함한다.

### 변경 대상

| 파일 | 변경 |
| --- | --- |
| `HousingDataController.java` | `supplementalOnly` 요청값 검증·전달 |
| `AnnouncementRepository.java` | `CatalogQuery`와 SQL 조건, 적용 필터 응답 보강 |
| `AnnouncementRepositoryTests.java` | 일반·추가모집·마감 공고 조합의 필터 테스트 |
| `public/app.js` | 기존 요청/초기화 동작이 서버 응답과 일치하는지 확인 |

### 완료 기준

- 체크 시 추가모집 공고만 반환된다.
- 해제 시 기존 결과와 같다.
- 진행 상태·지역·금액 조건과 함께 적용된다.
- 페이지네이션의 전체 건수와 다음 페이지 여부가 필터 결과를 기준으로 계산된다.

## 3. 기관별 PDF 파서 확대

### 입력 자료와 경계

- 실제 원본은 `data/pdf-fixtures/`에 있으며 Git에는 넣지 않는다.
- 기관·문서 유형은 관리자가 선택한 `siteCode`와 `documentType`으로만 결정한다. PDF 본문으로 기관을 추측하지 않는다.
- 서울주거포털은 현재 SH 원문으로 연결되는 유입 경로이므로, 고유 PDF 템플릿이 확인되기 전에는 별도 파서를 만들지 않는다.
- 지원사업 PDF는 주택 공고와 구조가 달라 이번 범위에서 제외한다.

### 작은 구현 단위

#### 3-1. LH 핵심 공공임대

- 대상: `LH / HAPPY_HOUSING_NOTICE`, `LH / NATIONAL_RENTAL_NOTICE`
- 기존 `LhPublicRentalPdfParser`를 실제 샘플 기준으로 보강한다.
- 목표: 단지·주소, 주택형·면적·공급호수, 임대조건, 일정, 신청 조건을 추출하되 표 셀 관계·단위가 불확실하면 값을 비우고 `검토 필요` 근거와 경고만 남긴다.
- 실제 행복주택·국민임대 샘플 최소 5건에 대한 회귀 테스트를 추가한다. 로컬 원본이 없으면 테스트는 명시적으로 건너뛰되, 합성 템플릿 테스트는 항상 실행한다.

#### 3-2. SH 공공임대

- 대상: `SH / PUBLIC_RENTAL_NOTICE`
- 샘플 7건을 표 구조별로 분류하고, 공통 표 구조에서만 값을 읽는다.
- 공급 위치·주택형·면적·공급호수·보증금·월세·일정을 우선한다.
- 유형마다 표 구조가 달라 확신할 수 없는 행은 추정하지 않는다.

#### 3-3. 관리자 선택지와 서울주거포털 경로

- 지원되는 기관과 문서 유형만 드롭다운에 노출한다.
- 서울주거포털 경로로 유입된 SH 원문은 `SEOUL_HOUSING_PORTAL / SH_PUBLIC_RENTAL_NOTICE` 키를 명시적으로 SH 파서에 연결한다.
- 원문 PDF가 LH이면 LH 키를 별도로 지원할 때까지 선택지에 노출하지 않는다.

### 공통 완료 기준

- 각 값에는 페이지·원문·좌표·추출 방식·검토 상태가 있다.
- 자동 파서는 항상 초안만 만들며 불확실한 값은 `검토 필요`로 남긴다.
- 관리자 수정·검증·확정 후에만 사용자 카드·상세 API에 반영된다.
- 기관별 실제 샘플 5건 이상과 합성 템플릿의 회귀 테스트가 있다.

## 검증 순서

1. Java 단위·통합 테스트 실행
2. Node 프론트 계약 테스트 실행
3. PDF 검토 화면에서 미검토 근거 확정 차단과 완료 후 확정 확인
4. 공고 찾기에서 추가모집 토글, 상태·지역 조합, 페이지 이동 확인
5. LH·SH 지원 조합/미지원 조합의 업로드와 관리자 선택지 확인
