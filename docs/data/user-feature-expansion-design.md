# 개인화·공고 변경·비교·검색 저장 기능 설계

> 상태: 단계 1~4 구현 완료. 계정 동기화·개인 알림은 후순위 보류.
> 대상: React 웹(`web`) · Spring Boot API(`spring-app`) · SQLite

## 1. 목표와 범위

사용자가 공고를 찾고 선택하는 흐름을 아래 네 기능으로 보완한다.

1. 관심 저장 공고의 메모·알림 시점·정렬을 계정에 연결해 여러 기기에서 동일하게 사용한다.
2. 공고의 핵심 조건이 바뀌면, 무엇이 어떻게 달라졌는지 확인할 수 있게 한다.
3. 관심 공고 2~3개를 같은 기준으로 비교한다.
4. 자주 쓰는 검색 조건을 이름으로 저장하고 다시 적용한다.

현재 브라우저에만 저장되는 관심 공고, 메모, 알림 시점은 유지한다. 계정 기능이 도입되기 전에도 기존 사용 흐름이 깨지지 않아야 한다.

## 2. 현재 구조 활용 원칙

| 현재 구조 | 확장 방식 |
| --- | --- |
| `catalogFilters.ts`의 관심 공고·메모·알림 시점 Local Storage | 저장소 인터페이스로 감싸고, 비로그인은 Local Storage, 로그인 후에는 API 저장소를 사용한다. |
| `detail_revisions`와 `DetailRevisionDiff` | PDF 확정·상세 정보 갱신 전후의 차이를 공고 변경 이벤트로 변환한다. |
| 공고 상세의 단지·주택형·임대 조건·일정·신청 조건 데이터 | 비교 API가 동일한 상세 구조를 반환하고 비교 화면에서 재사용한다. |
| URL 기반 검색 조건 | 저장 검색은 현재 URL 조건 중 재사용 가능한 값만 저장하고, 적용 시 검색 URL을 갱신한다. |

원문에 없는 금액·면적·지역을 추정하지 않는다. 값이 없으면 비교와 변경 이력 모두 `공고문 확인` 또는 `정보 없음`으로 표시한다.

## 3. 권장 구현 순서

### 사용자 가치 기준 순서

1. **공고 변경 감지**: 이미 상세 이력 구조가 있어 가장 빠르게 실제 효용을 제공한다.
2. **공고 비교**: 로그인 없이도 관심 저장 공고를 비교할 수 있다.
3. **검색 조건 저장**: 현재 검색 조건 모델을 재사용해 구현 위험이 낮다.
4. **계정 연동**: 여러 기기 동기화에는 필요하지만 인증 방식·보안 정책 결정이 선행돼야 한다.

### 계정 동기화가 최우선인 경우

휴대폰과 PC 동기화가 먼저 필요하면, 1번 전에 최소 로그인·사용자 저장소 기반을 먼저 만든다. 이후 비교 선택, 저장 검색, 변경 알림 수신 설정을 같은 사용자 데이터 모델에 연결한다.

## 4. 관심 저장 데이터의 계정 연동

> 상태: **후순위 보류**. Google OAuth 로그인과 관심 저장 동기화 기반은 구현되어 있으나, 운영 우선순위에서는 뒤로 미룬다. 현재 기본 동작은 브라우저 Local Storage다.

### 4.1 사용자 경험

- 비로그인 사용자는 지금처럼 즉시 관심 저장, 메모, 알림 시점을 사용할 수 있다.
- 로그인 후 처음 한 번 `이 기기에 저장된 관심 공고를 계정에 합칠까요?`를 표시한다.
- 합치기를 선택하면 기존 관심 공고, 정렬, 메모, 알림 시점이 계정에 저장된다.
- 계정 동기화 재개 시 다른 기기에서도 같은 관심 공고 목록과 메모·알림 시점을 보게 한다.
- 로그아웃해도 서버 데이터는 유지하며, 이 기기의 임시 Local Storage 데이터와 섞지 않는다.

### 4.2 인증 결정 사항

Google OAuth 로그인과 `users`·`user_identities`·`user_saved_announcements` 기반은 준비되어 있다. 다만 계정 저장을 모든 화면에 공통 적용하고, 여러 기기 동기화를 운영 흐름으로 제공하는 작업은 보류 상태다. 현재 기본 사용 흐름은 Local Storage다.

| 방식 | 장점 | 고려 사항 |
| --- | --- | --- |
| 이메일 일회용 링크 | 비밀번호를 직접 보관하지 않아 단순하다. | 메일 발송 서비스와 도메인 설정이 필요하다. |
| 외부 로그인(OIDC) | 비밀번호·가입 화면을 직접 만들지 않는다. | 제공자 설정과 콜백 URL 관리가 필요하다. |
| 아이디·비밀번호 | 외부 서비스 없이 시작할 수 있다. | 비밀번호 해시, 재설정, 잠금, 보안 정책까지 직접 운영해야 한다. |

권장안은 **이메일 일회용 링크 또는 OIDC**다. 어떤 방식이든 프론트는 `GET /api/me`만 보고 로그인 상태를 판단해 인증 공급자 교체 영향을 최소화한다.

### 4.3 데이터 모델

```text
users
  id, display_name, created_at, updated_at, last_login_at

user_identities
  id, user_id, provider, provider_subject, email, verified_at, created_at
  UNIQUE(provider, provider_subject)

user_saved_announcements
  user_id, announcement_id, display_order, note, reminder_at,
  created_at, updated_at
  PRIMARY KEY(user_id, announcement_id)

```

- 현재 로그인 세션은 Spring Security 기본 세션을 사용하며 별도 `user_sessions` 테이블에는 저장하지 않는다. 서비스 재시작 뒤에는 다시 로그인할 수 있다.
- `user_saved_searches`와 개인 변경 알림 테이블은 계정 동기화 재개 단계에서 추가한다.
- 메모와 알림 시점은 `user_saved_announcements`의 공고별 속성으로 저장한다.
- 공고 삭제·비공개 전환 시에도 사용자 저장 행은 즉시 삭제하지 않고, 화면에서 `더 이상 제공되지 않는 공고`로 분리 표시하거나 정리할 수 있게 한다.

### 4.4 API

| API | 역할 |
| --- | --- |
| `GET /api/me` | 로그인 사용자와 기본 상태 조회 |
| `GET /api/me/saved-announcements` | 관심 저장 공고와 개인 속성 조회 |
| `PUT /api/me/saved-announcements/{announcementId}` | 저장, 메모, 알림 시점 갱신 |
| `DELETE /api/me/saved-announcements/{announcementId}` | 관심 저장 해제 |
| `PUT /api/me/saved-announcements/order` | 저장 순서 일괄 변경 |
| `POST /api/me/migrate-local-state` | 최초 로그인 시 Local Storage 데이터 병합 |

`migrate-local-state` 병합 규칙:

1. 공고 ID는 중복 없이 합친다.
2. 이 기기의 정렬 순서를 우선하고, 서버에만 있던 공고는 뒤에 유지한다.
3. 서버 메모·알림이 비어 있을 때만 이 기기 값을 채운다.
4. 처리 결과를 반환해 사용자가 합쳐진 개수를 확인할 수 있게 한다.

### 4.5 프론트 구조

`SavedAnnouncementStore` 인터페이스를 만들고 아래 두 구현을 둔다.

```ts
type SavedAnnouncementStore = {
  list(): Promise<SavedAnnouncement[]>;
  save(input: SavedAnnouncementInput): Promise<void>;
  remove(announcementId: string): Promise<void>;
  reorder(ids: string[]): Promise<void>;
};
```

- `LocalSavedAnnouncementStore`: 기존 `catalogFilters.ts` Local Storage 키를 그대로 읽는다.
- `ApiSavedAnnouncementStore`: 로그인 상태에서 위 API를 호출한다.
- 화면 컴포넌트는 저장 위치를 직접 알지 않고 Store만 사용한다.

### 4.6 완료 기준

- 로그인한 두 기기에서 관심 공고·순서·메모·알림 시점이 일치한다.
- 기존 브라우저 저장 데이터는 최초 로그인 때 유실 없이 병합된다.
- 로그아웃, 세션 만료, 네트워크 실패 시 화면이 잘못 저장됐다고 표시하지 않는다.
- 다른 사용자의 관심 공고 ID를 조회·수정할 수 없다.

## 5. 공고 변경 감지

### 5.1 감지 대상과 제외 대상

사용자 의사결정에 직접 영향을 주는 필드만 변경 알림 대상으로 삼는다.

| 구분 | 감지 대상 |
| --- | --- |
| 임대 조건 | 보증금, 월세, 관리비, 전환 조건 |
| 일정 | 접수 시작·마감, 당첨 발표, 계약, 입주 일정 |
| 모집 | 사용자용 진행 상태, 추가모집 여부, 공급 호수 |
| 공급 주택 | 주소, 단지명, 주택형, 전용면적, 동·층·호 |

다음은 변경 이벤트를 만들지 않는다.

- PDF 근거 좌표·원문 문구만 바뀐 경우
- 표 행 순서 변경, 공백·표기법만 변경된 경우
- 최초 PDF 확정으로 상세 데이터가 처음 생성된 경우
- 관리자 메모·검토 상태만 바뀐 경우

원문 상태와 사용자용 상태 범주는 모두 보존한다. 예를 들어 `추가모집`은 모집 방식으로, `진행 중`은 사용자용 진행 상태로 별도 비교한다.

### 5.2 데이터 모델

```text
announcement_change_events
  id, announcement_id, detail_revision_id,
  category, field_path, before_json, after_json,
  occurred_at, created_at

announcement_change_notifications
  id, user_id, announcement_change_event_id,
  channel, delivered_at, read_at, created_at
  UNIQUE(user_id, announcement_change_event_id, channel)
```

- `category`: `RENTAL_CONDITION`, `SCHEDULE`, `RECRUITMENT`, `HOUSING`.
- `field_path`: 예: `sites[0].rentalOptions[1].depositAmount`, `events.application.endDate`.
- `before_json`, `after_json`: 표시용 문자열이 아닌 원본 정규화 값과 단위를 함께 저장한다.
- 이벤트는 기존 `detail_revisions`의 revision ID를 참조해, 왜 변경되었는지 PDF 이력까지 추적할 수 있게 한다.

### 5.3 생성 흐름

```text
PDF 확정 또는 상세 데이터 갱신
  → 변경 전 스냅샷 확보
  → 상세 데이터 저장
  → 변경 후 스냅샷 확보
  → DetailRevisionDiff로 의미 있는 필드만 비교
  → announcement_change_events 저장
  → 관심 저장 사용자별 알림 후보 생성
```

- 상세 데이터 저장과 변경 이벤트 저장은 같은 DB 트랜잭션에서 처리한다.
- 실패 시 상세 데이터만 저장되고 변경 이벤트가 누락되는 상태가 없어야 한다.
- 공고별 마지막 비교 스냅샷은 기존 확정 revision을 기준으로 잡는다.

### 5.4 사용자 화면

- 공고 카드: 최근 7일 내 핵심 변경이 있으면 `보증금 변경`, `접수 마감 변경`처럼 한 줄만 표시한다.
- 공고 상세 Drawer: `변경 이력` 탭에서 변경 일시, 이전 값, 변경 값, 공식 공고문 링크를 표시한다.
- 관심 저장 목록: `새 변경` 필터와 읽음 처리 제공.
- 변경이 여러 개면 `임대 조건 2건 변경`처럼 요약하고, 상세에서 개별 필드를 확인한다.

변경 문구 예시:

```text
11월 14일 · 임대 조건 변경
보증금: 10,000,000원 → 12,000,000원
월세: 400,000원 → 380,000원
```

값이 여러 주택형에 걸쳐 있으면 반드시 주택형·동·호 또는 공급 위치를 함께 표시한다. 서로 다른 주택형의 가격을 같은 조건처럼 비교하지 않는다.

### 5.5 API와 완료 기준

| API | 역할 |
| --- | --- |
| `GET /api/announcements/{id}/changes` | 특정 공고의 공개 변경 이력 조회 |
| `GET /api/me/announcement-changes` | 관심 공고 기준의 변경 목록·읽음 상태 조회 |
| `PATCH /api/me/announcement-changes/{id}` | 읽음 처리 |

- PDF 확정 후 금액·일정·모집 상태 변경이 정확히 이벤트로 남는다.
- 동일 revision을 다시 처리해도 중복 이벤트·중복 알림이 생기지 않는다.
- 최초 상세 입력은 변경 알림으로 노출되지 않는다.
- PDF 검토 화면의 기존 revision 이력과 사용자용 변경 이력은 같은 revision으로 연결된다.

## 6. 공고 비교

### 6.1 진입과 선택 규칙

- 관심 저장 목록과 공고 카드에 `비교에 담기` 선택 상자를 둔다.
- 최소 2개, 최대 3개를 선택한다.
- 상단 고정 작업 바에 `비교하기 (2/3)` 버튼을 표시한다.
- 비교 선택은 URL `compare` 파라미터와 화면 상태에만 보관한다. 비교 자체를 DB에 저장하지 않는다.
- 계정 연동 전에도 Local Storage 관심 공고로 사용할 수 있다.

### 6.2 비교 화면

경로: `/compare?ids={id1},{id2},{id3}`

| 구역 | 표시 내용 |
| --- | --- |
| 상단 | 선택 공고명, 저장 해제, 다른 공고로 교체 |
| 기본 정보 | 지역·공급기관·공고 유형·모집 상태·공식 공고문 |
| 비용·면적 | 보증금·월세·관리비·전용면적·공급 호수 |
| 일정 | 접수 기간·마감일·당첨 발표·계약·입주 |
| 공급 주택 | 단지와 주택형별 선택 영역, 개별 임대 조건 |
| 신청 조건 | 연령·무주택·소득·자산·순위 |

- 데스크톱은 공고가 열(column), 비교 항목이 행(row)인 표다.
- 모바일은 첫 항목 열을 고정하고 가로 스크롤을 지원한다.
- `다른 값만 보기` 토글로 모두 같은 항목은 접을 수 있다.
- 누락값은 `공고문 확인`으로 통일하며 빈칸 또는 `0원`으로 표시하지 않는다.

### 6.3 여러 공급 위치·주택형 처리

공고 하나에 여러 단지·주택형·임대 조건이 있을 수 있으므로 카드 첫 번째 값을 대표값으로 비교하면 안 된다.

1. 기본 비교 영역에는 공고 공통 정보만 표시한다.
2. `공급 주택 비교` 영역에서 각 공고별 단지와 주택형을 사용자가 선택한다.
3. 선택한 주택형의 보증금·월세·면적·동·층·호·공급 호수를 같은 행에서 비교한다.
4. 기본 선택은 `전체 공급 주택`이며, 이때 비용은 `최저~최고` 범위와 `주택형별 상이`를 함께 표시한다.

### 6.4 API

`GET /api/announcements/compare?ids=id1,id2,id3`

- 2~3개 ID만 허용한다.
- 일반 공고 상세 조회와 같은 확정 데이터를 반환한다.
- 존재하지 않거나 공개 대상이 아닌 공고는 응답에서 제외하고, 화면에 제외 사유를 표시한다.
- 요청 순서대로 결과를 반환해 사용자의 비교 열 순서를 유지한다.

### 6.5 완료 기준

- 2~3개 공고를 선택해 금액·면적·지역·마감일을 한 화면에서 비교할 수 있다.
- 다중 단지·주택형 공고에서 임의의 첫 가격을 대표값처럼 보이지 않는다.
- 모바일에서 표가 잘리지 않고 가로 이동할 수 있다.

## 7. 검색 조건 저장

### 7.1 저장 대상

현재 공고 찾기에서 사용하는 아래 조건을 저장한다.

- 시·도, 시·군·구, 읍·면·동
- 공급기관, 주택 유형
- 사용자용 진행 상태, 추가모집만 보기
- 보증금·월세·전용면적 범위
- 마감 공고 포함, 정보 미확인 포함, 마감 임박만 보기
- 정렬 방식

다음 조건은 저장하지 않는다.

- 페이지 번호
- `관심 저장만`, `알림 시점 도래만` 같은 개인 화면 상태
- `내 관심 조건 일치`: 별도로 저장한 관심 조건을 참조하는 동적 필터이므로 저장 검색에 포함하지 않는다.
- 비교 선택 상태

### 7.2 사용자 흐름

1. 사용자가 검색 조건을 설정하고 `검색`을 누른다.
2. 검색 결과 상단의 `현재 조건 저장`을 누른다.
3. 이름을 입력한다. 예: `서울 청년 · 보증금 1억 이하`.
4. 저장된 검색 목록에서 선택하면 초안 필터와 적용 필터를 함께 바꾸고 검색을 실행한다.
5. 저장 검색의 이름 변경·덮어쓰기·삭제를 지원한다.

저장 검색을 적용해도 기존의 `draftFilters`와 `appliedFilters` 분리 원칙을 유지한다. 필터 입력만 바꿨다고 결과가 즉시 바뀌지 않고, 적용 동작을 완료한 뒤 결과를 갱신한다.

### 7.3 저장 구조

초기에는 Local Storage를 쓰되, 계정 연동 뒤에도 동일한 도메인 모델을 사용한다.

```ts
type SavedSearch = {
  id: string;
  name: string;
  filters: CatalogFilters;
  createdAt: string;
  updatedAt: string;
};
```

- 비로그인 키: `housing-monitor-saved-searches-v1`.
- 로그인 후에는 `user_saved_searches.filters_json`에 동일한 구조로 저장한다.
- 이름은 1~30자, 사용자별 최대 20개로 제한한다.
- 이름 중복 시 새로 만들지 않고 덮어쓰기 여부를 묻는다.

### 7.4 API

| API | 역할 |
| --- | --- |
| `GET /api/me/saved-searches` | 저장 검색 목록 조회 |
| `POST /api/me/saved-searches` | 새 검색 조건 저장 |
| `PATCH /api/me/saved-searches/{id}` | 이름·조건 갱신 |
| `DELETE /api/me/saved-searches/{id}` | 저장 검색 삭제 |

계정 연동 전에는 같은 인터페이스의 Local Storage 구현을 사용해 화면 로직을 재사용한다.

### 7.5 완료 기준

- 현재 검색 조건을 이름 붙여 저장하고, 새로고침 후에도 다시 적용할 수 있다.
- 적용한 저장 검색은 URL과 결과 조건이 일치한다.
- 계정 동기화 도입 후 저장 검색도 다른 기기에서 조회·수정할 수 있다.

## 8. 공통 화면·접근성 규칙

- 저장·비교·변경 이력 동작의 성공·실패는 토스트와 `aria-live`로 알린다.
- 저장 실패 시 낙관적으로 바꾼 버튼 상태를 되돌리고 재시도 방법을 제공한다.
- 비교 선택·저장 검색 메뉴·변경 이력 Drawer는 Escape와 포커스 복귀를 지원한다.
- 금액은 `12,000,000원`, 면적은 `59m²`, 날짜는 `2026.11.14.`처럼 한 가지 표기 규칙을 사용한다.
- 개인 메모는 공고 카드의 공용 정보와 구분하고, 타 사용자·공개 API 응답에 포함하지 않는다.

## 9. 구현 단위와 검증

| 단계 | 작업 | 주요 검증 |
| --- | --- | --- |
| 1 | 공고 변경 이벤트 모델·생성 로직 | PDF 확정 전후 금액·일정·상태 차이, 중복 생성 방지 |
| 2 | 변경 이력 사용자 화면 | 카드 요약, 상세 이력, 다중 주택형 표시 |
| 3 | 비교 API·비교 화면 | 2/3개 제한, 누락값, 모바일 가로 스크롤 |
| 4 | 저장 검색 Local Storage | 저장·적용·수정·삭제, URL 및 검색 결과 일치 |
| 5 | 인증 기반·사용자 저장소 | 세션, 접근 제어, 관심 공고 동기화 |
| 6 | 기존 Local Storage 병합·저장 검색 동기화 | 중복·정렬·메모·알림 시점 병합, 다기기 확인 |
| 7 | 변경 알림 개인화 연결 | 관심 공고 사용자에게만 알림 후보 생성·읽음 처리 |

각 단계는 React build, 기존 공고 검색 회귀 테스트, Spring API·Repository 테스트를 통과해야 한다. 특히 변경 감지 단계는 PDF 확정과 복원, 상세 수동 수정, 같은 데이터 재확정의 세 경우를 모두 자동 테스트한다.

## 10. 구현 전 결정이 필요한 사항

1. 계정 방식: 이메일 일회용 링크, 외부 로그인(OIDC), 아이디·비밀번호 중 선택
2. 변경 알림 범위: 화면 내 이력만 먼저 제공할지, 이후 FCM·브라우저 푸시까지 동시에 연결할지
3. 비교 기준: 기본 비교를 `전체 공급 주택`으로 둘지, 첫 진입 시 사용자가 주택형을 반드시 고르게 할지

권장 기본값은 **이메일 일회용 링크**, **화면 내 변경 이력 우선 후 푸시 연결**, **전체 공급 주택으로 시작하고 주택형 선택을 제공**이다.
