# 개인화·공고 변경·비교·검색 저장 구현 작업지시서

> 기준 설계: [개인화·공고 변경·비교·검색 저장 기능 설계](./user-feature-expansion-design.md)  
> 원칙: 한 단계씩 구현·검증·검토를 끝낸 뒤 다음 단계로 진행한다.

## 1. 공통 작업 원칙

- 현재 공고 검색, 관심 저장, PDF 확정, 상세 Drawer, 기존 API 동작을 깨지 않게 한다.
- 공고 상세의 값이 없을 때 임의의 금액·면적·주소를 만들지 않는다.
- React 화면은 기존 공통 컴포넌트와 스타일 규칙을 재사용한다.
- 서버 저장 변경은 SQLite migration, Repository 테스트, API 테스트를 함께 추가한다.
- 개인 메모·알림 시점은 공개 공고 API 응답에 포함하지 않는다.
- 각 단계 완료 전 `npm.cmd run build`, 관련 프론트 테스트, 관련 Spring 테스트를 실행한다.
- 단계별 변경은 독립적으로 커밋 가능한 단위로 유지한다.

## 2. 단계 1 — 공고 변경 이벤트 저장

### 목표

PDF 확정 또는 상세 공고 수정 시, 사용자에게 의미 있는 공고 조건 변경을 정규화해 저장한다.

### 작업 내용

1. `announcement_change_events` 테이블 migration을 추가한다.
   - `id`, `announcement_id`, `detail_revision_id`, `category`, `field_path`, `before_json`, `after_json`, `occurred_at`, `created_at`
   - 공고 ID, revision ID, 발생 시각 조회 인덱스를 추가한다.
2. 기존 `detail_revisions`와 `DetailRevisionDiff` 구조를 확인하고 재사용한다.
3. 다음 값만 변경 이벤트로 만든다.
   - 보증금, 월세, 관리비, 전환 조건
   - 접수 시작·마감, 당첨 발표, 계약, 입주 일정
   - 사용자용 진행 상태, 추가모집 여부, 공급 호수
   - 주소, 단지명, 주택형, 전용면적, 동·층·호
4. 다음 변경은 이벤트에서 제외한다.
   - PDF 근거 원문·좌표만 변경된 경우
   - 공백, 표기 순서만 변경된 경우
   - 최초 PDF 확정으로 상세 정보가 처음 저장된 경우
   - 관리자 검토 상태·메모만 변경된 경우
5. PDF 확정·복원·상세 수동 수정 흐름에서 변경 전후 스냅샷을 비교한다.
6. 상세 데이터 저장과 변경 이벤트 저장은 같은 트랜잭션으로 처리한다.
7. 동일 revision의 이벤트 중복 생성을 방지한다.

### 완료 기준

- 보증금, 월세, 접수 마감일, 진행 상태 변경이 각각 이벤트로 저장된다.
- 최초 상세 입력은 사용자용 변경 이벤트로 저장되지 않는다.
- 같은 데이터를 다시 확정해도 중복 이벤트가 생기지 않는다.
- PDF 확정과 복원 후에도 기존 revision 이력이 유지된다.

### 검증

- 변경 이벤트 Repository·Service 테스트를 추가한다.
- 금액 변경, 일정 변경, 상태 변경, 무의미한 변경, 최초 입력, 중복 확정 케이스를 테스트한다.
- 기존 PDF 확정·복원 테스트를 실행한다.

## 3. 단계 2 — 공고 변경 이력 사용자 화면

### 목표

공고 카드와 상세 Drawer에서 최근 핵심 변경과 필드별 변경 내역을 이해하기 쉽게 보여 준다.

### 작업 내용

1. `GET /api/announcements/{id}/changes` API를 추가한다.
   - 변경 일시 내림차순으로 반환한다.
   - 공고 공개 범위와 기존 상세 조회 규칙을 따른다.
2. 공고 카드에는 최근 7일 이내 변경이 있을 때 한 줄 요약만 표시한다.
   - 예: `보증금 변경`, `접수 마감 변경`, `임대 조건 2건 변경`
3. 상세 Drawer에 `변경 이력` 탭 또는 동등한 진입점을 추가한다.
4. 상세 이력은 이전 값 → 변경 값, 변경 일시, 변경 대상 주택형·단지, 공식 공고문 링크를 표시한다.
5. 여러 주택형의 변경은 주택형·동·층·호 또는 공급 위치를 함께 표시한다.
6. 값이 없을 때 `0원`, 빈칸, 추정값 대신 `공고문 확인` 또는 `정보 없음`으로 표시한다.

### 완료 기준

- 카드에서 최근 변경 여부를 과도한 배지 없이 확인할 수 있다.
- 상세 화면에서 변경 전후 값과 대상 주택형을 구분할 수 있다.
- 공고 이력 없음 상태, API 실패 상태, 로딩 상태가 자연스럽게 보인다.
- 키보드 탭 이동과 Drawer 포커스 규칙을 유지한다.

### 검증

- 변경 이력이 있는 공고와 없는 공고를 각각 확인한다.
- 모바일 폭 360px에서 변경 행이 잘리지 않는지 확인한다.
- 공고 상세 Drawer의 기존 탭·닫기·공식 공고문 링크 회귀를 확인한다.

## 4. 단계 3 — 공고 비교 API와 화면

### 목표

관심 저장 공고 2~3개를 지역, 비용, 면적, 일정, 신청 조건 기준으로 비교한다.

### 작업 내용

1. 관심 저장 목록과 공고 카드에 `비교에 담기` 선택 UI를 추가한다.
   - 최소 2개, 최대 3개만 선택 가능
   - 선택 수를 표시하는 고정 작업 바 제공
   - 2개 미만일 때 `비교하기` 비활성화
2. 비교 화면 경로를 `/compare?ids=id1,id2,id3`로 추가한다.
3. `GET /api/announcements/compare?ids=...` API를 추가한다.
   - 2~3개 ID만 허용
   - 요청한 순서대로 결과 반환
   - 존재하지 않거나 사용자 화면에 노출할 수 없는 공고는 제외 사유 반환
4. 비교 화면은 공고가 열, 비교 항목이 행인 표 구조로 만든다.
   - 기본 정보: 지역, 공급기관, 공고 유형, 모집 상태, 공식 공고문
   - 비용·면적: 보증금, 월세, 관리비, 전용면적, 공급 호수
   - 일정: 접수 기간, 마감일, 당첨 발표, 계약, 입주
   - 신청 조건: 연령, 무주택, 소득, 자산, 순위
5. 다중 단지·주택형 공고는 임의의 첫 값을 대표값으로 사용하지 않는다.
   - 기본은 `전체 공급 주택` 범위로 표시
   - 공고별 단지·주택형을 선택하면 선택한 조건의 비용·면적을 비교
   - 값이 여러 개인 경우 `주택형별 상이`를 명시
6. `다른 값만 보기` 토글을 제공한다.
7. 모바일에서는 첫 열을 고정하고 표는 가로 스크롤 가능하게 한다.

### 완료 기준

- 관심 저장 공고 2~3개를 선택하고 비교 화면으로 이동할 수 있다.
- 누락값은 `공고문 확인`으로 일관되게 표시된다.
- 다중 주택형 공고가 잘못된 대표 가격으로 비교되지 않는다.
- 비교 화면에서 공고 제거·교체가 가능하다.

### 검증

- 1개, 2개, 3개, 4개 선택 시도를 각각 확인한다.
- 다중 주택형, 상세 미확인, 삭제·비노출 공고를 포함해 확인한다.
- 360px 모바일 및 데스크톱에서 표 가독성을 확인한다.

## 5. 단계 4 — 검색 조건 저장: 브라우저 우선

### 목표

로그인 없이도 자주 쓰는 검색 조건을 이름 붙여 저장·적용·수정·삭제한다.

### 작업 내용

1. `SavedSearch` 도메인 모델과 Local Storage 저장소를 추가한다.
   - 키: `housing-monitor-saved-searches-v1`
   - `id`, `name`, `filters`, `createdAt`, `updatedAt`
2. 공고 찾기 결과 상단에 아래 UI를 추가한다.
   - 저장된 검색 선택 목록
   - `현재 조건 저장`
   - 저장 검색 이름 변경·삭제
3. 저장 대상은 아래 조건으로 제한한다.
   - 지역 계층, 공급기관, 주택 유형, 사용자용 진행 상태, 추가모집
   - 보증금·월세·전용면적 범위
   - 마감 공고 포함, 정보 미확인 포함, 마감 임박, 정렬
4. 저장하지 않는 조건은 제외한다.
   - 페이지 번호, 관심 저장만, 알림 시점 도래만, 내 관심 조건 일치, 비교 선택
5. 저장 검색 적용 시 `draftFilters`와 `appliedFilters`를 동시에 일관되게 설정하고 검색을 실행한다.
6. 이름은 1~30자, 최대 20개로 제한한다.
7. 이름 중복 시 덮어쓰기·취소 선택을 제공한다.

### 완료 기준

- 조건을 저장한 뒤 새로고침해도 목록에서 다시 적용할 수 있다.
- 저장 검색 적용 후 URL, 적용 조건 요약, 결과가 일치한다.
- 검색 조건 입력만으로 결과가 즉시 바뀌지 않는 기존 동작을 유지한다.

### 검증

- 저장·적용·이름 변경·덮어쓰기·삭제·최대 개수·중복 이름을 확인한다.
- 지역 계층 및 금액·면적 범위가 정확히 복원되는지 확인한다.
- 기존 검색·초기화·정렬·관심 필터 회귀를 확인한다.

## 6. 단계 5 — 계정 기반과 관심 저장 동기화

> 상태: **후순위 보류**. Google OAuth 로그인과 계정 저장 기반은 준비되어 있지만, 전체 화면 공통 저장소 연결·기기 간 동기화를 운영 흐름으로 제공하는 작업은 진행하지 않는다. 현재 기본 흐름은 Local Storage다.

### 시작 전 확인 사항

구현 시작 전에 인증 방식을 확정한다.

- 권장: 이메일 일회용 링크 또는 OIDC
- 비권장: 별도 보안 설계 없이 아이디·비밀번호를 먼저 도입하는 방식

인증 방식이 정해지지 않았다면 DB 스키마와 화면 연결까지만 준비하고, 실제 로그인·세션 발급은 구현하지 않는다.

### 작업 내용

1. 인증 방식에 맞춘 `users`, `user_identities`를 추가한다. 별도 세션 저장소가 필요한 경우에만 `user_sessions`을 추가한다.
2. `user_saved_announcements` 테이블을 추가한다.
   - 사용자·공고 복합 키
   - 순서, 메모, 알림 시점, 생성·수정 시각
3. 세션은 원문 토큰이 아닌 해시만 서버에 저장한다.
4. `GET /api/me`, 관심 저장 조회·저장·삭제·정렬 API를 만든다.
5. 프론트에 `SavedAnnouncementStore` 인터페이스를 추가한다.
   - 비로그인: 기존 Local Storage 구현
   - 로그인: API 구현
6. 최초 로그인 시 Local Storage 병합 화면과 `POST /api/me/migrate-local-state`를 구현한다.
   - 기기 순서 우선, 서버 전용 공고는 뒤에 추가
   - 서버 메모·알림이 비어 있을 때만 기기 값을 채움
7. 로그아웃·세션 만료·오프라인 실패 시 저장 상태를 잘못 성공으로 보이지 않게 처리한다.

### 완료 기준

- 로그인한 서로 다른 기기에서 관심 저장 공고, 순서, 메모, 알림 시점이 일치한다.
- 기존 Local Storage 데이터가 병합 과정에서 유실되지 않는다.
- 다른 사용자의 저장 데이터는 접근·수정할 수 없다.

### 검증

- 사용자 A/B 접근 제어 테스트를 추가한다.
- 로컬 병합의 중복 ID, 정렬, 메모, 알림 시점 조합을 테스트한다.
- 세션 만료·API 실패 시 UI 복구를 확인한다.

## 7. 단계 6 — 저장 검색 계정 동기화와 변경 알림 개인화

> 상태: **보류**. Google 로그인·관심 저장 동기화 기반은 구현되어 있으나, 이 단계의 저장 검색 동기화와 개인 변경 알림은 현 우선순위에서 제외한다.

### 목표

저장 검색을 계정에 동기화하고, 관심 저장 공고에 한해 변경 이력을 개인 목록으로 제공한다.

### 작업 내용

1. `user_saved_searches` 테이블과 CRUD API를 추가한다.
2. 단계 4의 Local Storage 검색 조건을 최초 로그인 시 서버와 병합한다.
3. `announcement_change_notifications` 테이블을 추가한다.
4. 공고 변경 이벤트 생성 시 관심 저장 사용자에 대해 중복 없는 알림 후보를 만든다.
5. `GET /api/me/announcement-changes`, 읽음 처리 API를 추가한다.
6. 관심 저장 목록에 `새 변경` 필터와 읽음 상태를 추가한다.
7. 이 단계에서는 화면 내 알림함을 우선 구현한다. 브라우저 알림·FCM은 별도 푸시 설계 문서를 기준으로 다음 단계에 연결한다.

### 완료 기준

- 저장 검색이 로그인한 다른 기기에서도 동일하게 보인다.
- 관심 저장한 공고의 새 변경만 개인 변경 목록에 나타난다.
- 같은 이벤트가 같은 사용자에게 중복 표시되지 않는다.

### 검증

- 저장 검색 병합·동기화·삭제를 확인한다.
- 관심 공고와 비관심 공고의 변경 알림 대상을 구분한다.
- 읽음·미읽음 상태와 중복 방지를 확인한다.

## 8. 최종 검토 체크리스트

### 기능

- [ ] 변경 이벤트가 실제 공고 조건 변경에만 생성된다.
- [ ] 공고 비교는 다중 주택형의 값을 잘못 단순화하지 않는다.
- [ ] 저장 검색이 검색 URL·결과와 일치한다.
- [ ] 로그인 전 Local Storage 기능이 그대로 동작한다.
- [ ] 로그인 후 개인 저장 데이터가 기기 간 동기화된다.

### 데이터·보안

- [ ] 개인 메모·알림 시점이 공개 공고 API에 노출되지 않는다.
