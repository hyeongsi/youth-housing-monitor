# 공고 데이터 관리 화면 구현 계획

작성일: 2026-11-12  
상태: 구현 전 설계 검토용

## 1. 목적

관리자가 `PDF 검토`, `PDF 관리`의 차이를 이해하거나 내부 상태 코드를 해석하지 않아도 다음 일을 끝낼 수 있게 한다.

1. 어떤 공고에 PDF가 필요한지 찾는다.
2. PDF를 연결하고 자동 분석한다.
3. 확인이 필요한 정보만 PDF 원문과 비교한다.
4. 검토한 정보를 사용자 공고 화면에 반영한다.
5. 여러 확정 공고의 핵심 정보를 한 표에서 비교·수정하고 변경 이력을 남긴다.

새 화면은 관리자용 `공고 데이터 관리`이며, 기존 SQLite 테이블과 PDF 초안·근거·확정 이력 구조를 재사용한다. 같은 데이터를 두 번 저장하거나 사용자용 API에 초안·관리 근거를 노출하지 않는다.

## 2. 정보 구조

### 관리자 메뉴

```text
수집 관리 | 공고 데이터 관리
```

`공고 데이터 관리`의 내부 탭은 다음 세 개다.

| 탭 | 목적 | 기본 진입 여부 |
| --- | --- | --- |
| 작업함 | PDF 등록·검토·운영 반영을 건별로 처리 | 기본 탭 |
| 일괄 편집 | 반영된 공고의 핵심 데이터를 비교·수정 | 별도 탭 |
| 반영 이력 | 확정·복원·수동 수정 이력을 확인 | 별도 탭 |

`PDF 검토`, `PDF 관리`는 독립 메뉴에서 제외하고 새 화면의 하위 흐름으로 통합한다. 기존 `/admin-import.html`, `/admin-imports.html` 주소는 이미 만든 초안의 링크가 깨지지 않도록 유지하고, 동일한 검토 화면 또는 새 작업함의 해당 항목으로 이동시킨다.

### 상태 용어

화면에는 DB 코드값을 표시하지 않는다.

| 화면 상태 | 계산 기준 | 행의 주 행동 |
| --- | --- | --- |
| PDF 필요 | 주택 공고에 연결된 분석 초안 없음 | PDF 등록 |
| 분석 실패 | 최신 초안이 분석 실패 | 다시 분석 |
| 확인 필요 | 최신 초안에 미확인 근거 또는 검증 오류 존재 | 검토 계속 |
| 반영 가능 | 최신 초안의 검증·근거 확인 완료, 아직 미확정 | 운영 반영 |
| 반영 완료 | 최신 초안이 확정됨 | 이력 보기 |
| 상세 확보 | PDF 초안은 없지만 HTML 상세 수집 결과가 있음 | 상세 보기 |
| PDF 미지원 | PDF 상세가 없고 지원 파서 조합도 없음 | 지원 대기 |

- `DRAFT`, `READY`, `COMMITTED`, `MATCHED`, `NEEDS_REVIEW` 등은 API·DB 내부에서만 유지한다.
- `원문과 같음`은 `CONFIRMED`, `직접 수정함`은 `MANUALLY_REVIEWED`로 변환한다.
- 사용자용 공고 목록에는 확정된 상세 데이터만 표시한다.
- `PDF 필요`은 **지원 파서 조합이 있고**, 확정 PDF 상세와 HTML 상세 수집 결과가 모두 없는 공고에만 사용한다. PDF를 처리할 수 없는 공고는 기본 작업함에 섞지 않고 `PDF 미지원` 필터에서만 보인다.

## 3. 화면 설계

### 3-1. 작업함

첫 진입 화면이다. 카드 남용 대신 목록 행을 사용하며, 한 행에는 하나의 주 행동만 둔다.

```text
공고 데이터 관리                                      [PDF 등록]
공고문 PDF를 연결하고, 확인이 필요한 정보만 검토해 운영 화면에 반영합니다.

확인 필요 12   반영 가능 3   PDF 필요 7   반영 완료 48

[확인 필요] [반영 가능] [PDF 필요] [전체]     [공고명·기관 검색]

세이지움 개봉 청년안심주택 추가모집
서울 구로구 · 청년안심주택 · PDF 1개
보증금·월세 2건, 신청 조건 1건을 확인해야 합니다.                  [검토 계속]

LH 행복주택 입주자 모집
경남 의령군 · 행복주택 · PDF 없음
상세정보를 채우려면 공고문 PDF를 등록하세요.                       [PDF 등록]
```

#### 동작

- 상태 요약 또는 상태 칩을 누르면 해당 작업만 필터링한다.
- `PDF 등록`은 해당 공고가 미리 선택된 등록 단계로 이동한다.
- `검토 계속`은 최신 PDF 초안을 열고, 미확인 묶음을 처음으로 연다.
- `운영 반영`은 반영 전 변경 요약을 먼저 보여 준다.
- `이력 보기`는 공고별 반영 이력 탭을 연다.
- 목록 대상은 `content_kind='ANNOUNCEMENT'`인 활성 공고만 사용한다. 당첨·서류 제출 같은 안내 게시물은 포함하지 않는다.
- HTML 상세가 이미 수집된 공고는 PDF 등록 대상으로 표시하지 않고 `상세 확보`로 구분한다. PDF를 추가 등록하려면 상단 `PDF 등록`에서 명시적으로 시작한다.

### 3-2. PDF 등록·검토 흐름

작업함에서 이어지는 단일 흐름이다. 업로드 뒤 관리자 목록으로 돌려보내지 않는다.

```text
공고 데이터 관리 / 세이지움 개봉 청년안심주택 추가모집

1 공고 연결 ─── 2 PDF 분석 ─── 3 정보 확인 ─── 4 운영 반영
```

#### 단계 1. 공고 연결과 PDF 등록

- 작업함에서 들어온 경우 공고는 자동 선택하고 제목·기관·공식 URL을 읽기 전용으로 보여 준다.
- 상단 `PDF 등록`에서 들어온 경우에만 공고 검색·선택을 노출한다.
- 기관·문서 유형은 공고의 수집 출처로 기본 선택한다. 지원 조합이 하나면 선택 UI를 숨기고, 둘 이상이면 명확한 설명과 함께 선택하게 한다.
- 파서 목록은 화면에 상수로 중복 작성하지 않고 서버의 지원 조합 목록에서 받는다.
- 동일 hash PDF가 이미 있으면 오류로 끝내지 않고 `기존 분석 열기`를 제공한다.

#### 단계 2. 분석 결과 요약

분석 완료 후 다음 다섯 묶음의 진행 상태만 먼저 보여 준다.

| 묶음 | 포함 데이터 |
| --- | --- |
| 단지·위치 | 단지명, 주소, 기관 역할 |
| 주택형·면적 | 주택형, 면적, 공급호수, 동·층·호 |
| 보증금·월세 | 보증금, 월세, 관리비, 전환 조건 |
| 일정 | 접수, 발표, 계약, 입주 |
| 신청 조건 | 연령, 무주택, 소득, 자산, 순위 |

- `확인 필요 n건`인 묶음만 기본으로 펼친다.
- 완료 묶음은 접은 상태로 두되 열어 볼 수 있다.
- PDF 원문은 데스크톱 좌측에 고정하고, 선택한 필드의 페이지로 이동한다.
- 오른쪽의 긴 근거 목록은 제거한다. 선택한 필드의 근거만 입력값 바로 아래에 보인다.

#### 단계 3. 필드 확인

```text
보증금                 151,000,000원
PDF 원문               151,000,000 (단위: 원)

[원문과 같음] [직접 수정함]
```

- `원문과 같음`은 모든 연결 근거를 `CONFIRMED`로 저장한다.
- `직접 수정함`은 값을 편집 가능하게 하고 해당 필드에 `MANUALLY_REVIEWED` 근거를 만든다.
- 삭제된 필드는 근거도 삭제 상태가 되어 확정 검증 대상에서 제외된다.
- 기존 PDF 확정 안전장치를 유지한다. 미확인 근거가 하나라도 있으면 `운영 반영`은 비활성화하고, 필요한 필드명·건수를 안내한다.
- 초안은 명시적 `초안 저장`과 입력 후 자동 저장 중 하나만 사용한다. 이번 구현에서는 저장 상태가 불명확해지지 않도록 **명시적 `초안 저장`**을 유지한다.

#### 단계 4. 운영 반영

```text
운영 반영 전 확인
✓ 단지·위치 4건 확인 완료
✓ 주택형·면적 3건 확인 완료
! 보증금·월세 2건 확인 필요

[초안 저장] [운영 화면에 반영] (비활성화)
```

- 검증 오류가 없고 모든 근거가 확인된 경우에만 반영 버튼을 활성화한다.
- 반영 전에는 사용자 화면에 바뀌는 핵심 값(지역·보증금·월세·면적·일정)만 요약한다.
- 성공 후 `사용자 공고 보기`, `작업함으로`, `이력 보기`를 제공한다.
- 확정은 기존 트랜잭션과 `announcement_detail_revisions` 이력을 재사용한다.

### 3-3. 일괄 편집

일괄 편집은 PDF 검토의 대체 화면이 아니다. 확정된 공고의 핵심 정보를 비교하거나 작은 정정 사항을 처리하는 화면이다.

```text
일괄 편집
[반영 완료] [확인 필요 포함] [지역] [유형] [검색]

공고명                 지역       보증금        월세      전용면적    마감일       상태
세이지움 개봉           구로구     151,000,000   354,600   36.65㎡    11/20       반영 완료
LH 행복주택             의령군     미기재        미기재    26.84㎡    11/19       확인 필요
```

#### 범위 제한

- 첫 구현에서 표에 표시하는 값은 `지역/주소`, `보증금`, `월세`, `전용면적`, `접수 마감일`, `모집 상태`다.
- 이 중 목록 수집 원문이 기준인 `접수 마감일`, `모집 상태`는 **읽기 전용**이다. 다음 수집에서 원문 값으로 갱신되므로 일괄 편집 대상에 넣지 않는다.
- 첫 구현에서 직접 수정 가능한 값은 PDF·HTML 상세 계층에 저장되는 `지역/주소`, `보증금`, `월세`, `전용면적`뿐이다.
- 다단지·다주택형·다수 임대조건인 공고는 잘못된 행을 수정할 위험이 있으므로 표에서 직접 편집하지 않는다. `상세 검토`로 이동시킨다.
- 공고명, 공식 URL, 수집 출처, PDF 원문은 이 화면에서 수정하지 않는다.

#### 수정 흐름

1. 행을 선택하면 우측 편집 패널이 열린다.
2. 값 수정 후 `변경 내용 검토`를 누른다.
3. 이전값·이후값·수정 사유를 확인한다.
4. `변경 반영`을 누르면 한 공고 단위 트랜잭션으로 저장한다.

수정 사유는 `공고문 정정`, `입력 오류`, `정보 보완`, `기타` 중 선택한다. 직접 수정은 PDF 자동 추출의 확정 근거를 덮어쓰지 않고, 별도 `ADMIN_MANUAL_EDIT` 이력과 변경 사유를 남긴다. 목록 원문 필드의 수동 override 기능은 수집 우선순위·복원 범위 설계를 별도로 마치기 전까지 추가하지 않는다.

### 3-4. 반영 이력

- 공고별 확정 PDF, 복원, 일괄 직접 수정 이력을 시간 역순으로 표시한다.
- 행에는 작업 유형, 시각, 변경 요약, PDF hash 또는 수동 수정 사유를 표시한다.
- `변경 내용 보기`는 기존 필드별 이전값·이후값 비교를 재사용한다.
- 복원은 PDF 확정본에 대해서만 제공한다. 수동 편집 이력은 먼저 비교 화면을 보여 주고 재확인을 요구한다.

## 4. 데이터·API 설계

### 재사용

- `announcements`, `housing_sites`, `locations`, `supply_units`, `rental_options`, `announcement_events`
- `document_extractions`, `extraction_evidence`, `announcement_documents`
- `announcement_detail_revisions`
- `GET/PATCH /api/admin/document-imports/{id}`, validate, commit, PDF 원문 API

### 새 관리 API

| API | 역할 |
| --- | --- |
| `GET /api/admin/announcement-work-items?status=&query=&page=` | 작업함 행, 상태별 건수, 행의 다음 행동 반환 |
| `GET /api/admin/document-parser-options?announcementId=` | 해당 공고에서 선택 가능한 기관·문서 유형 반환 |
| `GET /api/admin/announcements/operational?query=&region=&status=&page=` | 일괄 편집 표용 확정 공고 핵심값 반환 |
| `PATCH /api/admin/announcements/{id}/operational-summary` | 허용된 상세 계층 핵심 필드의 수동 정정 초안 검증·저장 |
| `POST /api/admin/announcements/{id}/operational-summary/commit` | 수동 정정 확정 및 이력 저장 |

새 API의 응답은 목록에 필요한 값만 반환한다. PDF 원문, 전체 근거, 전체 상세 JSON은 행 목록 API에 넣지 않는다.

### 수동 정정 이력 보강

`announcement_detail_revisions`에 다음 선택 컬럼을 추가한다.

- `change_reason TEXT`: 선택한 수정 사유
- `change_source TEXT`: `PDF_COMMITTED`, `RESTORED`, `ADMIN_MANUAL_EDIT`

기존 행은 `change_source`를 기존 `action` 값으로 읽어 호환한다. 수동 정정은 기존 before/after JSON 스냅샷, 트랜잭션, 필드별 diff를 반드시 재사용한다.

수동 정정의 대상은 `detail()` 스냅샷에 포함되는 상세 계층으로 한정한다. `announcements.status`, `announcements.application_end` 같은 목록 원문 필드는 이 단위에서 수정하지 않으므로, 기존 상세 스냅샷과 복원 범위를 넓히지 않는다.

#### 위치·주소 수동 정정의 copy-on-write 규칙

`locations`와 `housing_sites`는 여러 공고가 공유할 수 있으므로, 일괄 편집 API는 기존 행을 `UPDATE`하지 않는다.

1. 주소·시도·시군구·읍면동 중 하나를 수동 수정하면 해당 `announcement_site` 전용 `locations`와 `housing_sites` 사본을 만든다.
2. 새 사본의 `canonical_key`는 기존 키를 재사용하지 않고 `announcement_id`와 수정 후 값을 포함한 새 키를 사용한다.
3. 해당 공고의 `announcement_sites.site_id`만 새 `housing_sites.id`로 교체한다.
4. 다른 공고가 참조하는 기존 위치·단지는 그대로 둔다.
5. 이 연결 변경도 before/after 상세 스냅샷과 `ADMIN_MANUAL_EDIT` 이력에 포함한다.

따라서 한 공고의 주소 정정이 다른 공고의 지도·지역 검색·상세 화면을 바꾸지 않는다. 보증금·월세·면적 수정은 이미 공고별 `supply_units`·`rental_options`에 연결돼 있으므로 같은 원칙으로 해당 공고 상세 행만 변경한다.

## 5. 파일별 변경 계획

## 6. 작은 작업 단위와 완료 기준

### 단위 0. 현재 화면 기준선·용어 정리

- 기존 경로와 API를 목록화하고 새 화면의 상태명 매핑을 확정한다.
- `style-guide.md`에 관리자 작업 화면 규칙을 기록한다.
- 완료: 기존 `/admin.html`, `/admin-import.html`, `/admin-imports.html`이 모두 열리고 새 문서와 충돌하지 않는다.

### 단위 1. 공고 데이터 관리 앱 셸과 작업함 읽기 화면

- `/admin-data.html`과 작업함 목록 API를 추가한다.
- 상태 요약, 필터, 검색, 다음 행동 한 개를 표시한다.
- PDF 업로드·확정 동작은 이 단위에서 복제하지 않는다.
- 완료: PDF 필요·확인 필요·반영 가능·반영 완료·상세 확보·PDF 미지원이 중복 없이 분류되고, 공고/안내 게시물이 분리된다.

### 단위 2. 작업함에서 PDF 등록으로 이어지는 흐름

- 행의 `PDF 등록`과 상단 등록 버튼에서 공고 선택을 넘긴다.
- 서버 지원 파서 조합으로 기관·문서 유형을 기본 선택한다.
- 중복 PDF는 기존 초안 열기로 전환한다.
- 완료: 등록 후 새 초안을 바로 검토 화면에서 열 수 있고, 뒤로 가도 작업함 필터 상태가 유지된다.

### 단위 3. 단계형 PDF 검토 UX

- 기존 3열 원문/입력/근거 구조를 유지하되, 다섯 정보 묶음 요약과 미확인 항목 우선 표시를 추가한다.
- 상태 드롭다운을 `원문과 같음`, `직접 수정함` 행동으로 교체한다.
- 확정 전 안내와 성공 후 이동을 명확히 한다.
- 완료: 관리자는 내부 상태코드 없이 미확인 필드만 처리해 확정할 수 있고, 기존 서버 검증을 우회할 수 없다.

### 단위 4. 반영 이력 통합

- 작업함·검토 화면에서 공고별 이력으로 이동한다.
- PDF 확정·복원 이력과 필드별 차이를 같은 UI에서 확인한다.
- 완료: 반영 후 사용자 공고 보기와 이력 보기를 모두 제공하며, 기존 복원 기능이 유지된다.

### 단위 5. 일괄 편집 읽기·필터 화면

- 확정 공고 핵심값만 페이지네이션 표로 표시한다.
- 지역·상태·검색·누락값 필터를 제공하고 다단지 행은 상세 검토로 보낸다. 접수 마감일·모집 상태는 읽기 전용으로 표시한다.
- 완료: 표가 1280px와 360px에서 읽히며, 모바일은 카드·상세 이동으로 전환된다.

### 단위 6. 일괄 편집 수동 정정·이력

- 허용된 단일값 필드만 우측 패널에서 수정한다.
- 변경 요약·수정 사유 확인 뒤 공고 단위로 확정한다.
- 수동 수정 이력과 기존 PDF 이력을 함께 표시한다.
- 완료: 변경 전후값·사유가 저장되고, 실패 시 운영 값과 이력이 바뀌지 않는다.

### 단위 7. 접근성·반응형·회귀 점검

- 키보드 탭 순서, 포커스 복귀, `aria-live`, 빈 상태, 로딩·실패·재시도, 360px/1280px를 점검한다.
- 완료: 작업함→등록→검토→반영→사용자 공고 확인 및 일괄 수정→이력 확인 흐름을 자동·수동으로 검증한다.

## 7. 구현 금지 사항

- 새 관리자 화면 때문에 기존 상세 데이터를 복제하거나 새 JSON 저장소를 만들지 않는다.
- PDF 파서가 불확실한 값을 자동 확정하지 않는다.
- 일괄 편집으로 다단지·다주택형·다중 임대조건을 임의로 수정하지 않는다.
- 사용자용 공고 API에 PDF 원문, 초안, 근거, 관리자 이력을 포함하지 않는다.
- 사용자 화면에 관리자용 내부 상태 코드·오류 메시지를 노출하지 않는다.

## 8. 검증 체크리스트

- 작업함 상태별 건수와 목록이 일치하는가
- 각 행의 주 행동이 하나이고, 다음 작업이 설명되는가
- PDF 등록 후 공고·기관·문서 유형이 올바르게 연결되는가
- 미확인 근거가 있으면 운영 반영이 차단되는가
- 확정 후 사용자 카드와 상세 Drawer가 DB 확정값을 보여 주는가
- 일괄 편집이 허용된 단일값만 수정하는가
- 직접 수정의 사유·전후값·시각이 이력에 남는가
- 뒤로 가기·새로고침에도 탭·필터·대상 공고 상태가 유지되는가
- 360px·1280px·키보드 조작에서 레이아웃과 포커스가 정상인가
