# 메뉴형 UI 개발 명세

## 1. 목적과 기준 파일

운영 화면을 `docs/ui/housing-menu-reference.html`과 `docs/ui/housing-menu-reference.css`의 정보 구조와 시각 밀도에 맞게 개선한다.

목업은 레이아웃·상태·상호작용 기준이며 예시 숫자와 공고는 운영 코드에 복사하지 않는다. 운영 화면에서는 `/api/overview`의 실제 데이터와 기존 저장·수집 로직을 사용한다.

## 2. 변경 범위

| 파일 | 변경 내용 |
| --- | --- |
| `public/index.html` | 화면별 DOM 배치, 요약 카드 컨테이너, 상세 검색 조건, 공고 Drawer 구조 정리 |
| `public/app.css` | 목업 기준 레이아웃, 카드 밀도, 검색 결과, 반응형, Drawer와 상태 표현 |
| `public/app.js` | 요약 계산, 홈 노출 제한, 필터 확장, Drawer 데이터 연결, 초기 검증, 수집 요약, 제도 더 보기 |

서버, API, 수집기, `data/*.json`은 UI 구현을 위해 임의로 변경하지 않는다. 상세 데이터가 없는 경우 UI에서 값을 추정하지 않는다.

## 3. 현재 구현에서 유지할 기능

- `VIEW_IDS`, `getViewFromHash()`, `setActiveView()` 기반 메뉴 전환
- `GET /api/overview`를 사용하는 `load()`
- `reloadPage()`의 중복 클릭 방지, 기존 데이터 유지, 토스트
- `catalogState.draftFilters`, `catalogState.appliedFilters`
- 10건 단위 `announcementLimit`과 더 보기
- `openAnnouncementDrawer()`, `closeAnnouncementDrawer()`의 초점 복귀와 Escape 처리
- `formatNumericInput()`, `setAreaValidation()`
- 관심 조건 localStorage와 `PUT /api/profile`
- `POST /api/monitor/refresh`, `GET /api/monitor/refresh` 폴링
- 미확인 값을 `공고문 확인 필요`로 표시하는 정책

## 4. 공통 앱 구조

### 시각 기준

| 항목 | 기준 |
| --- | --- |
| 글꼴 | OS 기본 sans-serif 우선. 외부 웹폰트 추가 금지 |
| 본문 | 14px, line-height 1.45 |
| 화면 제목 | 22~24px, 700 weight |
| 섹션 제목 | 16~18px, 700 weight |
| 일반 설명 | 12~13px |
| 보조 정보 | 11~12px. 정보 식별이 어려워지는 축소 금지 |
| 기본 간격 | 6, 8, 12, 16, 24px 조합 사용 |
| 입력 radius | 4px |
| 버튼 radius | 5px |
| 카드 radius | 5~6px |
| 강조색 | `#0867f2`. 주요 동작·선택 상태에만 사용 |
| 성공색 | 검증 완료·수집 성공에만 녹색 사용 |

과한 둥근 카드, 의미 없는 배지, 여러 단계의 그림자, 장식용 그라데이션을 추가하지 않는다. 화면마다 새로운 카드 스타일을 만들지 말고 요약 카드, 공고 카드, 정보 패널 세 종류로 제한한다.

### 버튼 배치

- 화면 전체 동작은 제목 오른쪽에 둔다. 모바일에서는 제목 아래 전체 너비로 배치한다.
- 폼 동작은 폼 하단 오른쪽에 `초기화`, `검색/저장` 순서로 둔다.
- 한 카드 안에 주요 버튼을 둘 이상 배치하지 않는다.
- 공고 상세의 주요 버튼은 Drawer 하단에 하나만 둔다.
- 아이콘만 있는 버튼에는 반드시 `aria-label`을 제공한다.

### 데스크톱

- 별도 브랜드 헤더를 두지 않고 좌측 메뉴와 본문이 화면 상단에서 바로 시작
- 사이드 메뉴: 176px, 흰색에 가까운 `#fbfcfe`, 우측 1px 구분선
- 본문 최대 너비: 1080px
- 본문 좌우 여백: 26px
- 메뉴 선택 상태: `#e8f2ff` 배경과 `#0867f2` 텍스트
- 카드 그림자는 제거하고 얇은 테두리로 구분
- 본문 바탕은 흰색. 회색 배경 위에 카드가 겹겹이 놓이는 대시보드 형태는 사용하지 않음

### 모바일

- 720px 이하에서 사이드 메뉴를 화면 상단의 가로 탭으로 전환
- 선택 탭은 배경색 없이 파란색 글자와 하단 3px 선으로 표시
- 각 메뉴 높이 56px, 조작 영역 최소 높이 44px
- 본문 좌우 여백 16px
- 카드, 필터, 폼은 1열
- 문서 가로 너비가 viewport를 넘지 않아야 함

## 5. 홈

### 요약 카드

기존 `#summary`의 설명 문장을 세 개의 요약 카드로 변경한다.

1. 이번 수집 신규 공고: `state.discoveries.length` 또는 `state.notifications.actionable.length`
2. 관심 조건 일치: `classifyInterest()` 결과가 `COMPARABLE`인 공고 수
3. 상세 확인 완료: `state.verifiedAnnouncements.length`

각 카드에는 제목, 건수, 한 줄 설명, 관련 화면 이동 링크만 둔다. 값이 없는 경우 `0건`으로 표시한다.

### 홈 공고 제한

- 관심 후보: 최대 3건
- 신규 공고: 최대 3건
- 상세 확인 완료: 최대 3건
- `COMPARABLE`을 `NEEDS_INFO`보다 먼저 표시
- 같은 등급에서는 접수 마감이 가까운 순으로 정렬
- 각 영역에 `전체 공고 보기` 링크 제공

홈에서 수천 건의 후보를 모두 렌더링하지 않는다. 전체 목록 탐색은 공고 찾기 화면의 역할이다.

### 공고 카드

표시 순서:

1. 모집 상태 또는 유형
2. 공고명
3. 지역
4. 보증금 / 월세
5. 전용면적
6. 접수 마감
7. 상세 보기

목업의 `assets/housing-seoul.png`, `assets/housing-gyeonggi.png`, `assets/housing-incheon.png`는 카드 비율과 사진 배치를 확인하기 위한 시각 자료다. 운영에서는 공고 또는 공급기관이 제공한 실제 이미지 URL이 있을 때만 사진을 노출한다. 이미지가 없으면 출처 약어와 건물 아이콘으로 만든 중립 타일을 사용하며, 목업 사진을 실제 공고 사진처럼 재사용하지 않는다.

사진이 있는 경우 카드 상단을 가로로 채우고 `object-fit: cover`를 사용한다. 3열 카드 높이는 약 132px, 검색 결과 썸네일은 48×48px로 맞춘다.

### 문구 원칙

- 화면 제목과 설명은 한 번씩만 표시한다.
- `최신 정보를 제공합니다`, `빠르게 확인하세요` 같은 의미가 모호한 홍보 문구를 반복하지 않는다.
- 현재 상태와 다음 행동을 구체적으로 쓴다. 예: `이번 수집 신규 12건`, `비용·면적 공고문 확인 필요`.
- 정보가 없는 상태와 오류 상태를 같은 문구로 처리하지 않는다.

## 6. 공고 찾기

### 필터 상태

`createDefaultCatalogFilters()`에 다음 값을 포함한다.

```js
{
  query: '',
  region: '',
  housingType: '',
  status: '',
  information: '',
  source: '',
  depositMaxWon: null,
  monthlyRentMaxWon: null,
  areaMin: null,
  areaMax: null,
  includeUnknown: true,
  newOnly: false,
}
```

- 입력·선택 이벤트는 `draftFilters`만 변경한다.
- 검색 버튼과 검색어 Enter만 `appliedFilters`를 갱신한다.
- 검색 실행 시 `announcementLimit`을 10으로 초기화한다.
- 초기화는 폼과 두 필터 상태를 모두 기본값으로 되돌린다.

### 필터 선택지

- 지역: `item.area`의 실제 값에서 생성
- 주택 유형: `item.housingType`의 실제 값에서 생성
- 출처: `item.sourceName`
- 상태: `item.status`

빈 값과 `목록 기재 없음`은 선택지에서 제외한다.

### 비용 필터

보증금과 월세 조건은 하나의 `costOptions` 항목이 동시에 만족해야 한다. 보증금은 한 조합, 월세는 다른 조합에서 가져와 통과시키지 않는다.

상세 비용이 없을 때:

- `includeUnknown === true`: 결과에 남기고 `공고문 확인 필요` 표시
- `includeUnknown === false`: 숫자 조건 결과에서 제외

미확인 금액을 `0`으로 취급하지 않는다.

### 면적 필터

- 검증된 `exclusiveAreaText` 또는 구조화된 면적값만 비교
- 문자열에서 안전하게 숫자를 추출할 수 없는 경우 미확인으로 처리
- 최소보다 최대가 작으면 검색하지 않고 인라인 오류 표시

### 결과 목록

데스크톱 우선 정보:

- 공고명·출처·정보 상태
- 지역
- 보증금 / 월세
- 전용면적
- 접수 마감·상태
- 상세 보기

별도 `비교 정보` 열은 제거하고 공고명 아래에 `비용·면적 확인됨` 또는 `공고문 확인 필요`를 표시한다.

`#all-announcements`의 고정 높이와 내부 세로 스크롤을 제거한다. 페이지 자체 스크롤과 `공고 더 보기` 버튼을 사용한다.

모바일에서는 table header를 숨기고 각 행을 카드형으로 재배치한다. 가로 스크롤을 만들지 않는다.

## 7. 공고 상세 Drawer

### 동작

- 카드와 결과 행의 상세 버튼에서 `openAnnouncementDrawer(item, detail, trigger)` 호출
- 앱 전체에 Drawer는 하나만 존재
- 닫기 버튼, backdrop, Escape로 닫기
- 열기 전 trigger를 저장하고 닫을 때 초점 복귀
- 모바일에서는 전체 폭

### 표시 데이터

항상 표시 가능한 목록 정보:

- 공고명
- 출처와 공급기관
- 지역
- 주택 유형
- 모집 상태
- 공고일
- 접수 마감
- 공식 공고문 링크

검증된 상세 정보가 있을 때만 표시:

- 보증금
- 월세
- 전용면적
- 비용 조합의 조건

미확인 항목은 보증금, 월세, 전용면적별로 각각 `공고문 확인 필요`라고 표시한다. 값을 추정하거나 목업 값을 사용하지 않는다.

공식 공고문 버튼은 Drawer 하단의 sticky action 영역에 둔다.

## 8. 관심 조건

### 폼 배치

- 관심 지역: 전체 너비
- 보증금 / 월세: 데스크톱 2열
- 전용면적 최소 / 최대: 데스크톱 2열
- 모바일: 모두 1열
- 현재 적용 조건 요약을 폼 상단에 표시
- 초기화와 저장 버튼을 같은 행에 배치

### 숫자와 검증

- 표시값에는 3자리 쉼표
- 비교·저장값에는 쉼표 제거
- 음수와 숫자 이외 문자는 제거
- 빈 값은 `0`이 아니라 미설정

`setAreaValidation()` 호출 시점:

1. localStorage 값을 폼에 채운 직후
2. 관심 조건 화면 진입 시
3. 최소·최대 입력 변경 시
4. 저장 직전

최소가 최대보다 크면 오류를 바로 표시하고 저장을 중단한다. 두 필드에 `aria-invalid="true"`를 설정하고 최소 필드로 초점을 이동한다.

### 추가 프로필

`#profile-form`은 `추가 프로필 메모` details 안에 배치하고 기본은 접힌 상태로 둔다. 서버 저장 기능과 `자동 필터링에는 사용하지 않음` 안내를 유지한다.

## 9. 공고 수집

### 요약 영역

세 값을 한 줄로 표시한다.

- 마지막 성공 수집: `allAnnouncements.checkedAt || monitor.lastSuccessfulAt`
- 수집 결과: `monitor.outcome`
- 전체 공고 수: `allAnnouncements.itemCount`

같은 마지막 성공 시각을 화면에 중복 출력하지 않는다.

### 기관별 표시

`allAnnouncements.items`를 이용해 `sourceId → sourceName` Map을 만든다. 기관 이름을 찾을 수 없을 때만 source ID를 fallback으로 보여 준다.

각 행은 기관명, 성공/오류 상태, 수집 건수만 우선 표시한다. 오류 행에는 오류 요약과 `기존 마지막 정상 데이터 유지` 안내를 제공한다.

### 수집 중

서버가 정확한 진행률을 제공하지 않으므로 퍼센트를 표시하지 않는다.

- 버튼 비활성화
- 아이콘 회전
- `공식 목록을 수집 중입니다.`
- 퍼센트 없는 indeterminate bar
- 완료 후 `load()` 호출

## 10. 제도 안내

- 기존 프로그램 순서를 유지
- 최초 6개만 표시
- `제도 더 보기` 버튼으로 나머지 표시
- 기본 카드에는 제도명, 유형, 기관만 표시
- `자세히 보기` 버튼으로 비용·자격·공식 링크 확장
- 실제 button에 `aria-expanded`, `aria-controls` 적용
- 카드 전체에 가짜 button role을 사용하지 않음

## 11. 접근성과 상태

- 메뉴: `aria-current="page"`
- 비활성 화면: `hidden`
- 검색 결과·수집 상태·토스트: `aria-live="polite"`
- Drawer: `role="dialog"`, `aria-modal="true"`, `aria-labelledby`
- 모든 버튼과 메뉴 최소 높이 44px
- `:focus-visible` 유지
- `prefers-reduced-motion`에서 애니메이션 최소화
- 공식 링크: `target="_blank"`, `rel="noopener noreferrer"`, 새 탭 안내 포함

## 12. 구현 순서

1. `public/app.css`의 공통 레이아웃과 모바일 규칙 정리
2. 홈 요약과 최대 3건 미리보기 구현
3. 검색 필터 상태와 결과 목록 개선
4. Drawer 정보 항목과 sticky action 보완
5. 관심 조건 2열 배치와 초기 검증 수정
6. 공고 수집 요약과 기관명 매핑
7. 제도 6건 미리보기와 확장
8. 데스크톱·모바일·키보드 회귀 검증

## 13. 완료 기준

### 데스크톱 1280×820

- 홈 첫 화면에서 요약 3개와 주요 공고 3개 확인 가능
- 관심 후보 수천 건이 홈을 점유하지 않음
- 검색 결과에 내부 세로 스크롤 없음
- 관심 조건이 2열로 정돈됨
- 수집 핵심 상태 3개가 한눈에 보임
- 제도 안내 최초 노출이 6개 이하

### 모바일 360×800

- `document.documentElement.scrollWidth === 360`
- 메뉴, 필터, 카드, Drawer가 잘리거나 겹치지 않음
- 필터와 공고 결과가 1열
- Drawer 전체 폭
- 모든 주요 조작 대상 높이 44px 이상

### 기능 회귀

- hash 전환, 뒤로 가기, 앞으로 가기
- 검색 전 결과 유지와 검색 후 적용
