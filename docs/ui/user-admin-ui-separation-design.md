# 사용자 화면과 관리자 화면 분리 설계

## 1. 목적

현재 화면에는 사용자가 공고를 탐색할 때 필요한 정보와 운영자가 수집 상태를 확인할 때 필요한 정보가 함께 노출되어 있다. 사용자 화면은 공고 검색·비교·상세 확인에 집중하고, 수집 상태와 수동 수집 기능은 별도의 관리자 화면으로 분리한다.

이번 개편의 우선순위는 다음과 같다.

1. 사용자가 공고명, 지역, 보증금, 월세, 전용면적, 접수 기간을 빠르게 비교할 수 있게 한다.
2. 수집 건수와 검증 상태 등 내부 운영 정보를 사용자 화면에서 제거한다.
3. 확인되지 않은 값은 공고 단위의 상태가 아니라 해당 필드에만 `공고문 확인`으로 표시한다.
4. 전체 정보는 상세 Drawer와 공식 공고문에서 확인할 수 있게 한다.
5. 기존 API, 데이터 구조, 필터링과 관심 조건 판정 로직은 유지한다.

## 2. 현재 사용자 화면에서 제거할 정보

다음 정보는 사용자에게 공고 선택을 돕지 않으므로 사용자 화면에서 제거한다.

- 이번 수집 신규 공고 수
- 관심 조건 일치 공고 수
- 상세 확인 완료 공고 수
- 정보 확인 필요 공고 수
- 최근 수집 시각과 수집 결과
- 기관별 수집 상태
- 수집 실패 출처와 내부 오류
- `화면 다시 불러오기` 버튼
- `공고 수집` 메뉴
- `지금 공고 수집` 버튼

검색 결과 건수는 사용자가 검색 범위를 이해하는 데 필요하므로 유지한다.

## 3. 사용자 정보 구조

사용자 메뉴는 다음 네 개로 구성한다.

1. 홈
2. 공고 찾기
3. 관심 조건
4. 제도 안내

`#home`을 기본 진입 화면으로 사용한다. 홈에는 수집 건수나 검증 통계가 아니라 추천 공고와 최근 공고만 제한된 개수로 표시한다. 기존 `#collection`은 사용자 라우팅에서 제거한다.

### 3.1 홈 대시보드

홈은 사용자에게 공고를 발견하게 하는 화면이다. 운영 상태를 보여주는 통계형 대시보드로 만들지 않는다.

#### 화면 구성

1. 화면 제목과 짧은 설명
2. 추천 공고
3. 최근 공고
4. `전체 공고 보기` 버튼

추천 공고와 최근 공고는 각각 최대 3개만 표시한다. 데이터가 많아도 홈에서 추가 로딩하거나 무한 스크롤하지 않는다. 사용자가 더 보고 싶을 때 화면 하단의 `전체 공고 보기` 버튼을 눌러 `#announcements`로 이동한다.

#### 추천 공고

- 기존 관심 조건과 `classifyInterest()` 결과를 재사용한다.
- `COMPARABLE` 항목을 먼저 보여주고, 사용자가 정보 미기재 포함을 허용한 경우에만 `NEEDS_INFO`를 뒤에 배치한다.
- 추천은 신청 자격 판정이 아니라 저장한 관심 조건과의 비교 결과임을 짧게 안내한다.
- 관심 조건이 저장되지 않았다면 잘못된 추천을 만들지 않고 `관심 조건을 설정하면 지역·금액·면적 기준으로 공고를 모아볼 수 있습니다.` 안내와 `관심 조건 설정` 버튼을 표시한다.

#### 최근 공고

- `announcementDate`를 우선 사용해 최신순으로 정렬하고, 값이 없으면 기존 목록 순서를 유지한다.
- 최근 수집 건수나 수집 시각을 표시하지 않는다.
- `state.discoveries`에 포함된 실제 신규 공고만 카드에 `신규` 배지를 붙인다.
- 신규 공고가 없더라도 최근 공고 목록은 유지한다.

#### 홈 카드

- 기존 공고 카드 렌더링과 Drawer를 재사용한다.
- 공고명, 지역, 보증금, 월세, 전용면적, 접수 기간을 표시한다.
- 미확인 값은 해당 필드에만 `공고문 확인`으로 표시한다.
- 카드 전체를 별도 구현으로 복제하지 말고 공통 카드 생성 함수를 사용한다.
- 홈 카드의 상세 보기와 공식 공고문 링크는 공고 찾기 화면과 같은 동작을 해야 한다.

#### 전체 공고 보기

- 홈의 두 섹션 아래에 하나의 명확한 버튼으로 배치한다.
- 버튼 클릭 시 `#announcements`로 이동한다.
- 메뉴 상태와 문서 제목이 공고 찾기로 변경되어야 한다.
- 기존에 사용자가 적용해 둔 검색 조건은 임의로 삭제하지 않는다.

### 3.2 공고 찾기

#### 검색 영역

- 지역 또는 공고명 통합 검색
- 지역
- 주택 유형
- 모집 상태
- 보증금 상한
- 월세 상한
- 전용면적 최소·최대
- 정보가 미기재된 공고 포함 여부
- 관심 조건에 맞는 공고만 보기
- 관심 저장한 공고만 보기
- 초기화
- 검색

필터 입력은 `draftFilters`, 실제 검색 결과는 `appliedFilters`를 계속 사용한다. 입력값 변경만으로 결과를 바꾸지 않고 `검색` 버튼이나 검색창 Enter로 적용한다.

#### 검색 결과 제목

사용자에게는 다음 정보만 표시한다.

```text
검색 결과 42건
```

`전체 목록`, `마지막 성공 수집`, `상세 확인 완료`, `정보 확인 필요` 같은 내부 상태 문구는 표시하지 않는다.

#### 공고 정보 우선순위

1. 공고명
2. 지역
3. 보증금
4. 월세
5. 전용면적
6. 접수 기간 또는 마감일
7. 모집 상태
8. 공급기관

확인되지 않은 값은 해당 필드에만 `공고문 확인`으로 표시한다. 금액·면적·지역을 추정하지 않는다.

### 3.3 공고 카드

데스크톱의 공고 카드는 같은 행에서 동일한 높이를 유지한다. 카드 내부를 다음 영역으로 구분한다.

```html
<article class="notice-card verified-card">
  <div class="verified-card-header">...</div>
  <dl class="notice-facts">...</dl>
  <div class="verified-card-footer">
    <div class="verified-card-meta">...</div>
    <div class="verified-card-actions">...</div>
  </div>
</article>
```

`notice-facts`는 `(지역, 보증금) / (월세, 전용면적)` 순서의 2×2 구분선 구조로 표시한다. 단일 검증 조건은 실제 금액, 복수 조건은 `조건별 상이`, 값이 없으면 해당 필드에만 `공고문 확인`을 표시한다.

표시 줄 수는 다음과 같이 제한한다.

| 영역 | 표시 기준 |
| --- | --- |
| 공고명 | 최대 2줄 |
| 출처·목록 상태 | 최대 1줄 |
| 지역·금액·면적 | 항목별 최대 2줄 |
| 접수 기간·모집 상태·공급기관 | 전체 최대 3줄 |

초과 텍스트는 CSS 말줄임으로 처리한다. 카드 전체에 `overflow: hidden`을 적용하지 않고 개별 텍스트 영역에만 적용하여 포커스 표시가 잘리지 않게 한다.

목록 카드에는 주택형별 비용 조건을 별도 영역으로 표시하지 않는다. 상세 Drawer에서는 전체 조건을 유지한다.

데스크톱 카드는 `min-height: 380px`을 기준으로 같은 행의 높이와 버튼 하단을 맞춘다. `720px` 이하에서는 최소 높이를 해제하고 줄 수 제한만 유지한다.

버튼 영역은 카드 하단에 고정한다.

- `상세 보기`: 보조 버튼
- `공식 공고문 보기`: 주요 버튼
- 버튼 높이 최소 `44px`
- 두 버튼 사이 간격 `8px`
- 공식 링크가 없으면 상세 보기 버튼이 전체 너비 사용
- `380px` 이하에서 두 버튼이 겹치면 한 열로 전환

### 3.4 공고 상세 Drawer

Drawer 상단에는 다음 핵심 정보를 우선 표시한다.

- 공고명
- 모집 상태
- 지역
- 보증금
- 월세
- 전용면적
- 접수 기간
- 입주 예정일
- 공급기관

다음 정보는 필요할 때 펼쳐보는 형태로 제공할 수 있다.

- 주택형별 보증금·월세 조건
- 신청 대상
- 소득·자산 조건
- 제출 서류
- 신청 전 확인 사항

하단에는 `관심 저장`, `공식 공고문 보기` 버튼을 둔다. Drawer는 Escape, 배경 클릭, 닫기 버튼을 지원하고 포커스를 내부에 유지한 뒤 닫을 때 원래 버튼으로 돌려보낸다.

### 3.5 관심 조건

다음 입력과 저장 기능만 제공한다.

- 관심 지역
- 보증금 상한
- 월세 상한
- 전용면적 최소·최대
- 정보가 미기재된 공고 포함 여부
- 초기화
- 저장

금액과 면적 입력은 화면에 3자리 쉼표를 표시하고 내부 비교값은 숫자로 유지한다. 최소 면적이 최대 면적보다 크면 구체적인 오류 문구와 `aria-invalid="true"`를 적용한다.

### 3.6 제도 안내

현재 제도 데이터를 유지한다. 공고 검색이나 수집 기능과 섞지 않고 읽기 중심 화면으로 제공한다.

## 4. 관리자 화면

관리자 기능은 별도 페이지 `public/admin.html`로 분리한다. 사용자 상단 메뉴에는 관리자 메뉴를 노출하지 않는다. 로컬 운영 편의를 위해 필요한 경우 사용자 화면 하단에 작은 `관리자` 링크만 둘 수 있다.

관리자 화면에는 다음을 제공한다.

- 마지막 성공 수집 시각
- 전체 수집 공고 수
- 신규 공고 수
- 갱신 공고 수
- 기관별 성공·실패 상태
- 실패 출처와 오류 요약
- 수집 진행 상태
- `지금 공고 수집` 버튼
- 성공·일부 실패·전체 실패·재요청 제한 피드백

관리자 JavaScript는 기존 API를 그대로 사용한다.

- `GET /api/overview`
- `GET /api/monitor/refresh`
- `POST /api/monitor/refresh`

사용자 화면은 `/api/overview` 응답에서 공고·상세·제도 데이터만 사용하고 수집 상태와 발견 건수는 렌더링하지 않는다.

`admin.html` 분리는 정보 구조 분리일 뿐 접근 제어가 아니다. 서비스를 외부에 공개할 경우 관리자 인증과 `POST /api/monitor/refresh` 권한 검사를 서버에 별도 구현해야 한다. 현재 로컬 전용 범위에서는 인증을 이번 작업에 추가하지 않는다.

## 5. 파일별 변경 계획

| 파일 | 변경 목적 | 주요 내용 |
| --- | --- | --- |
| `public/index.html` | 사용자 화면 구성 | 사용자용 홈 대시보드 추가, 수집 통계와 수집 화면은 계속 제외 |
| `public/app.js` | 사용자 기능 구성 | 추천·최근 공고 제한 렌더링, 공통 카드 재사용, 검색·관심 조건·Drawer·제도 안내 유지 |
| `public/app.css` | 사용자 UI 정돈 | 홈 섹션과 카드 그리드, 카드 높이·말줄임·버튼 정렬, 반응형 처리 |
| `public/admin.html` | 관리자 화면 추가 | 수집 현황과 수동 수집 UI |
| `public/admin.js` | 관리자 동작 분리 | 수집 상태 조회, 수동 수집, 상태 폴링과 토스트 |
| `public/admin.css` | 관리자 화면 스타일 | 기존 디자인 토큰을 재사용한 최소 스타일 |

새 UI 라이브러리나 CSS 프레임워크를 추가하지 않는다. 공통 스타일은 기존 `app.css`를 우선 재사용하고 관리자 전용 스타일만 `admin.css`에 둔다.

## 6. 사용자 DOM 정리 대상

다음 DOM은 사용자 화면에서 제거하거나 관리자 화면으로 이동한다.

- `#summary`
- `#interest-candidate-count`
- `#interest-candidates`
- `#new-announcement-count`
- `#new-announcements`
- `#collection-view`
- `#collection-status`
- `#collection-result`
- `#monitor`
- `#discoveries`
- `#collect-announcements`
- `#header-collection-time`
- `#reload`

DOM을 제거할 때 `app.js`의 선택자, 렌더링 함수와 이벤트 등록도 함께 제거하여 초기화 오류가 발생하지 않게 한다.

## 7. 유지해야 하는 동작

- hash 기반 사용자 화면 전환
- `#home` 기본 진입과 홈의 제한된 추천·최근 공고 렌더링
- 홈의 `전체 공고 보기`를 통한 `#announcements` 이동
- 검색 전 `draftFilters`, 검색 후 `appliedFilters` 분리
- 숫자 입력 쉼표 표시
- 관심 조건 로컬 저장
- 관심 공고 로컬 저장
- 공고 상세 Drawer
- 공식 공고문 새 탭 열기
- 값이 확인되지 않은 공고 정보의 비추정 원칙
- 빈 결과, 로딩, 오류 상태
- 키보드 조작과 `prefers-reduced-motion`

## 8. 반응형 기준

- `1440px`: 홈과 검색 결과 카드 최대 3열, 검색 조건 최대 4열
- `768px`: 홈과 검색 결과 카드 2열, 검색 조건 2열
- `360px`: 홈과 검색 결과 카드·필터 1열, Drawer 전체 화면
- 모든 화면에서 가로 스크롤과 버튼·텍스트 겹침 금지
- 주요 버튼과 입력의 조작 영역 최소 `44px`

## 9. 완료 기준

### 사용자 화면

- 첫 진입 시 사용자용 홈 대시보드가 표시된다.
- 홈에는 추천 공고와 최근 공고가 각각 최대 3개만 표시된다.
- 홈에는 수집 건수, 검증 건수, 정보 확인 필요 건수와 기관 상태가 표시되지 않는다.
- 관심 조건이 없을 때 추천을 임의로 만들지 않고 관심 조건 설정 안내를 표시한다.
- 홈의 전체 공고 보기 버튼이 공고 찾기로 이동한다.
- 사용자 메뉴에 공고 수집과 수집 통계가 없다.
- 공고명, 지역, 보증금, 월세, 면적, 접수 기간을 한 화면에서 비교할 수 있다.
- 확인되지 않은 값만 `공고문 확인`으로 표시된다.
- 카드 높이와 버튼 위치가 일관된다.
- 말줄임된 전체 정보는 Drawer에서 확인할 수 있다.
- 검색, 초기화, 관심 저장, 관심 조건, 제도 안내가 정상 동작한다.

### 관리자 화면

- 사용자 화면과 독립적으로 열린다.
- 기존 수집 상태와 기관별 결과를 표시한다.
- 수동 수집의 중복 실행을 막는다.
- 수집 성공, 일부 실패, 전체 실패와 제한 상태를 구분한다.
- 수집 완료 후 관리자 데이터를 다시 불러온다.

## 10. 구현 제약

- API와 데이터 파일을 변경하지 않는다.
- 서버와 모바일 앱을 변경하지 않는다.
- 실제 데이터를 목업 데이터로 바꾸지 않는다.
- 기존 사용자 변경분을 무단으로 덮어쓰지 않는다.
- 불필요한 대규모 리팩터링을 하지 않는다.
- 이번 작업에서 관리자 인증을 작동하는 것처럼 표현하지 않는다.
